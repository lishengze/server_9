## 任务：FTE 现货交易全流程 ID 全景 + 必填性 + 缓存优化分析
**时间**：14:30-15:00

### 工作内容
1. **ID 全景分析**：梳理 FTE 现货委托请求/应答/成交回报/撤单全流程所有 ID（`TradeOrderReq`/`TradeOrderER`/`CancelOrderReq`），区分外部输入 vs FTE 生成：
   - **FTE 内部核心**：`clordno`（`GetClOrdNO()` 自增，`order_map_[clordno]` 定位订单主键）、`clordid`（`GetClOrdID(market_id)` 按市场 36 进制递增，报盘给交易所）、`order_id`（交易所确认回报 `base_report.order_id`，API 转 `order_sys_no` 对外）
   - **客户端**：`client_seq_id`（委托/撤单请求号，FTE 回显）、`agw_seq_id`（网关序号，预留 0）
   - **原单定位**：`orig_clordno`（FTE 定位原单主键）、`orig_client_seq_id`（协议保留）、`orig_clordid`（交易所撤单申报）
   - **成交**：`exec_id`（交易所去重键）、`index`（FTE 回报序号）
2. **必填性分析**：通过 FTE `CheckParams`/`DealCancelOrderReq` 校验逻辑确认：
   - 委托必填：`fund_account_id`/`branch_id`/`security_id`/`market_type`/`side`/`order_type`/`order_price`/`order_qty`（FTE 强校验）；`client_seq_id` 建议必填（回报关联）
   - 不必填：`account_id`/`cust_id`（session 回填）、`policy_id`/`tgw_id`（API 未使用）、`agw_seq_id`（预留 0）
   - 撤单必填：`client_req_no`/`fund_account_id`/`branch_id`/`order_sys_no`；`orig_client_seq_id`/`orig_clordno` API 自动反查
3. **缓存优化分析**：确认 `order_locators` 仅用于撤单；因 FTE 撤单只用 `orig_clordno`，若 `OrderRtn.order_sys_no` 改为返回 clordno，可去掉 `order_locators` 中间缓存（撤单从 3 次查找降为 1 次）。权衡：order_sys_no 语义变更对多柜台一致性的影响。
4. **补充文档**：`study/gw_counter.md` 新增 §4.3.3（ID 全景）、§4.3.4（必填性）、§4.3.5（缓存优化）；`study/knowledge_base_system/NewAPI_知识库.md` §11.3 同步 ID 全景速查 + 必填性速查。

### 结论
- FTE 内部用 clordno 定位订单，order_id（交易所编号）与 clordno 是两套独立编号体系，API 以 order_sys_no 对外、映射表桥接到 clordno。
- FTE 服务端真正强校验的是交易参数，账户 ID 多由 API/session 回填；policy_id/tgw_id 填了无效。
- **撤单中间缓存可优化**：`OrderRtn.order_sys_no` 改返回 clordno 后，可去掉 `order_locators`，但需评估 order_sys_no 语义变更的多柜台一致性。

### 经验教训
1. **必填性分析要看 FTE 服务端校验函数**（`CheckParams`/`DealCancelOrderReq`），而非只看 API 侧结构——API 填了不等于 FTE 校验，真正必填由服务端强校验决定。
2. **撤单定位原单只靠 orig_clordno**：orig_client_seq_id 在 FTE 撤单中完全不被使用，为后续缓存优化（去掉映射表）提供了可能。
