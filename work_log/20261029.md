### 工作内容
1. **定位推送失败根因**：`origin` 是 SSH 地址 `git@github.com:lishengze/server_9.git`，直连 `github.com:22/:443` 全部超时（`Test-NetConnection` 均 False）。
2. **验证 SSH 走代理不可行**：把 `connect.exe` 复制到无空格路径后用 `-H`/`-T` 建立 CONNECT 隧道，代理返回 `HTTP/1.1 200 Connection established`，但隧道内收不到 SSH banner（`Connection timed out during banner exchange`）→ **代理只放行 HTTPS，不放行 SSH**。`github.com:22`、`ssh.github.com:443`、`140.82.112.3:22` 三种组合结果一致。
3. **改用 HTTPS + 命令级代理推送成功**：
   ```powershell
   $env:GIT_TERMINAL_PROMPT='0'; $env:GCM_INTERACTIVE='never'
   git -c http.proxy=http://172.16.0.11:3128 push https://github.com/lishengze/server_9.git master
   # 667abe2..28778b1  master -> master
   ```
   凭据由 Windows 凭据管理器（`git:https://github.com`，用户 lishengze）提供，无需交互。代理对 `github.com` 偶发 502，重试即通。
4. **同步远端跟踪引用**：推的是 URL 不是 remote 名，`git status` 仍显示 `ahead 1` → `fetch <https-url> master` + `git update-ref refs/remotes/origin/master FETCH_HEAD`，之后显示 `## master...origin/master` 同步。
5. **取消代理并校验**：全程只用 `-c http.proxy=...` 单命令参数，`git config --local/--global --get http.proxy` 与 `https.proxy` 均为空，无残留；`remote -v` 仍为原 SSH 地址。

### 经验教训
1. **现象**：SSH 推送超时，先误以为"配 ProxyCommand 就能过代理"，反复试 `-H`/`-T`/端口 443 均失败。**根因**：代理对 SSH 只建隧道不转发（banner 收不到），是策略限制。**解法**：判定标准——`CONNECT` 返回 200 但 `banner exchange` 超时 = 代理不放行该协议，立即改 HTTPS 路线，不再调 SSH 参数。
2. **现象**：`push` 返回码 0、远端确实更新了，但 `git status` 仍显示 `ahead 1`。**根因**：推送目标是 HTTPS URL 而非 `origin`，远端跟踪引用 `refs/remotes/origin/master` 没更新。**解法**：推完 `fetch <url> <branch>` + `git update-ref refs/remotes/origin/master FETCH_HEAD`。**"推送成功"要同时满足：远端 SHA 一致 + 本地 tracking 同步 + 无代理残留**。
3. **现象**：代理对 `https://github.com/` 先返回 502、重试后 200。**根因**：代理出口偶发抖动。**解法**：重试 2~3 次再判定失败。
4. **现象**：`GIT_SSH_COMMAND` 里写含空格的 `C:/Program Files/...` 路径被 `/bin/sh` 拆断（`C:/Program: No such file or directory`）。**解法**：需要时先把可执行文件复制到无空格路径。
5. **流程**：`task_rule.md` §13 与 `review_prepare.sh` 在我工作时被其他会话/用户改动过，编辑时报"file changed since read"。**教训**：**并发环境下改动前先 `git status` + 重读文件**，只 `git add` 自己产出的路径，不用 `git add -A`。
