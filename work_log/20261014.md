### 经验教训
1. **现象**：`apt purge trae-cn` 报 `db_purge: command not found`，返回 exit 127。
   **根因**：trae-cn 的 postrm 脚本在 `[ "$1" = "purge" ] && [ -e '/usr/share/debconf/confmodule' ]` 条件下调用 `db_purge`，但脚本本身未 source confmodule，导致函数未定义（打包脚本 bug，非 debconf 缺失）。
   **解法**：删除 `/var/lib/dpkg/info/trae-cn.list` 和 `.postrm` 残留文件后，`dpkg --purge --force-all trae-cn` 可正常完成。
2. **现象**：sudo 在自动化终端无法交互输入密码。
   **解法**：用 `echo '密码' | sudo -S <命令>` 方式从标准输入读取密码执行提权操作。
3. 用户反馈中包名 `qcoder` 与系统实际 `qoder` 不符，执行删除前务必先 `dpkg-query` 确认包名，避免误删。

## 任务：修复 workspace-vdi 启动无反应问题
**时间**：09:10-09:20

### 工作内容
1. 定位启动链：`workspace_run.desktop` → `run.sh` → `RUN/start.sh` → `RUN/Workspace`（Qt5 + CEF）。
2. 逐层排查，发现三重依赖问题并逐一修复：
   - **libstdc++ 污染**：VS Code devchat 扩展注入 `LD_LIBRARY_PATH` 指向其自带旧版 libstdc++，缺 GLIBCXX_3.4.29/30/32 符号。修复：start.sh 开头加 `unset LD_LIBRARY_PATH`。
   - **libpcre.so.3 缺失**：Workspace 需旧版 PCRE，系统只有 PCRE2。修复：安装 `libpcre3`。
   - **quic 旧版 glib 污染**：`RUN/quic/` 下旧版 glib（2.56）缺 glib 2.80 新增符号 `g_once_init_leave_pointer`，被 LD_LIBRARY_PATH 优先加载导致 libatspi 加载失败。修复：重命名 quic 下 4 组旧 glib 库为 .bak，系统 glib 2.80 接管。

### 结论
- 修复后 Workspace 成功启动，进程 PID 34566 稳定运行，仅剩非致命警告（spaceagent 未装、ifname 缺失、CEF 沙箱警告等）。
- 备份：`start.sh.bak.20261014`、quic 下 glib 库 `.bak`。
- 新增安装 `libpcre3`，software_list.md 软件包总数 2162。

### 经验教训
1. **现象**：Workspace 启动无反应（静默崩溃）。
   **根因**：`LD_LIBRARY_PATH` 被 VS Code devchat 扩展污染，加载到旧版 libstdc++，缺 GLIBCXX 符号导致 Qt5 库加载失败。
   **解法**：启动脚本开头 `unset LD_LIBRARY_PATH`，排除 IDE 环境变量污染。
2. **现象**：qt5/CEF 应用报 `libpcre.so.3: cannot open shared object file`。
   **根因**：Ubuntu 24.04 默认只装 PCRE2，旧应用需旧版 PCRE。
   **解法**：安装 `libpcre3` 包。
3. **现象**：`libatspi.so.0: undefined symbol: g_once_init_leave_pointer`。
   **根因**：软件自带 quic 目录下旧版 glib（2.56）被 LD_LIBRARY_PATH 优先加载，缺 glib 2.80 新增符号。
   **解法**：重命名自带旧版 glib 库，让系统 glib 接管（glib 向后兼容）。
4. **通用排查法**：GUI 启动无反应时，用 `ldd <可执行文件>` 检查动态链接是否被污染；逐层修复 `LD_LIBRARY_PATH` 相关的库版本冲突。apt 命令也受 LD_LIBRARY_PATH 污染，需 `env -u LD_LIBRARY_PATH` 执行。

   - VDI 管理服务器 `10.104.241.10:8860` **可达**（登录/VM 列表正常）。

### 结论
- **黑屏根因**：云桌面通过 SPICE 协议（197.192.212.45:5937）连接，但该 SPICE 显示服务器不可达，云桌面画面无法渲染 → 黑屏；约 40 秒后 VdSession 超时退出 → 会话断开返回主界面（"关闭"）。
- **次要因素**：首次登录 80210 密码错误；CEF gpu-process 沙箱警告；日志提示 `read vpn info, decode passwd failed`，SPICE 地址可能需 VPN/办公网访问。
- 建议：确认当前网络/VPN 是否能访问 197.192.212.45，检查防火墙放行 5937/5900 端口，确认云桌面 VM（OA212209801）SPICE 服务正常。

### 经验教训
1. **现象**：workspace 能登录管理服务器、刷新 VM 列表，但连接云桌面后黑屏、约 40 秒断开。
   **根因**：VDI 采用"管理通道 + SPICE 显示通道"分离架构，管理服务器可达 ≠ 显示服务器可达；SPICE 显示端口（5937/5900）不可达导致黑屏。
   **解法**：用 `timeout 5 bash -c 'echo > /dev/tcp/IP/PORT'` 分别测试管理端口与显示端口连通性，定位不可达的是显示通道。
2. **排查法**：GUI 应用"启动正常但运行中黑屏"，优先区分启动问题与连接问题——看应用自身日志（`~/文档/Workspace/log/Workspace.log`）、会话进程（VdSession）是否存活、以及各依赖服务器端口连通性。
3. **VDI 架构认知**：Workspace 云桌面 = 管理服务器（登录/列表，8860）+ SPICE 显示服务器（画面渲染，5937/5900），两者网络可达性需分别验证。
