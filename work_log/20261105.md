### 经验教训
6. **拉取后第一件事是跑一致性校验器** → 现象：`sync_rules.sh -c` 立刻报副本不同步（上轮 `cp` 出的副本 vs 远程新增的生成式副本）。根因：规范副本 `cp` 与 `脚本生成` 两种做法并存。解法：只认 `bash task/sync_rules.sh`，拉取后先跑 `-c` 再动别的。
7. **知识库里的路径会随代码演进静默失效** → 现象：13 处路径 `test -e` 全 MISSING（FTE 多一层 `fte/`、`tech/net`→`tech/network`、`knowledge_base/` 目录被删、任务单改名、mock 文档迁到 `mock/doc/`）。根因：文档只写来源/索引，不写核对日期与核对命令，没人会主动复核。解法：把路径可靠性做成可执行动作——`test -e` / `find` 批量核，结论连同日期写进主文档（本次 §42.3），并写明「定位文件一律 `find`，不靠规则推」。
8. **表格多一列/少一列肉眼极难发现，必须机器校验** → 现象：新增的两行各多写一列（4 列 vs 表头 3 列），渲染后整表错位。根因：手写 markdown 表格无校验。解法：改表后用「按块统计 `|` 数、块内必须一致」的脚本过一遍（本轮已用，4 文件全绿）。
9. **「规律」比「单点事实」更容易骗人** → 现象：先总结出「FTE 路径要去掉重复的 fte/fte」，实测 `main.cpp` 恰在 `fte/fte/src/`。根因：把一条路径的观察升格成目录规则。解法：结论按「事实 + 适用范围」写，跨文件定位一律 `find`，并在文档里显式写出反例（§42.3 的两套源码树表）。
