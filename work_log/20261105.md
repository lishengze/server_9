### 经验教训
1. **环境事实必须按主机分版本记录** → 现象：知识库写着「本机 Windows 无 docker、只能做文档」，实际当前主机是 Linux 且 `otc` 容器在运行；照旧执行会把可编译可测试的任务误判为阻塞。根因：环境事实是「某台主机某时刻」的快照，却被写成无主机的绝对结论。解法：环境表按「当前主机（带日期）」+「历史主机（标注适用边界）」两段写，且每次跨主机开会话先用 `date`/`which`/`docker ps` 复核再信任文档。
2. **规则双份存储会漂移** → `task_rule.md`(353 行) 与 `.chat/rules/project_rules.md`(263 行) 已差出 §10.6（工具调用上限直接继续）与整个 §13（git 代理规则）。根因：`.chat/` 被 `.chat/.gitignore` 的 `*` 排除在版本库外（`git check-ignore` 实测命中），副本不随仓库走，各主机各一份且无同步检查。解法：以 `task/task_rule.md` 为唯一事实来源，改完立即整文件复制到 `.chat/rules/project_rules.md`（已写入 §10.3），收尾自检比对行数/关键字。
3. **验证式学习优于纯通读** → 用 grep 抽验 4 个关键符号（`send_req_msg` / `on_com_msg` / `GwLoginCache` / `FTE_DSE_FIFO_LEN`）即可确认文档与代码一致，成本极低却能提前发现「文档过期」这一最大风险；建议固化为每次读知识库后的固定动作。
