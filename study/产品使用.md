# API 框架产品使用指南

本指南面向接入此交易 API 的业务方开发人员，介绍整个生命周期中的使用规范、核心接口以及需要注意的避坑指南。

## 1. 业务接入与初始化流程

### 1.1 实例化 API 与配置
整个系统由 `api_config` 驱动，用户不需要关心复杂的依赖注入，只需配置参数即可：
```cpp
// 1. 创建配置实例
api_config* cfg = api_config::create_config();

// 2. 核心配置：柜台选型与网络地址
cfg->set_attr(config_name::fast_counter_type, "fpga_direct"); // 极速硬件
cfg->set_attr(config_name::fast_counter_ip, "192.168.1.100");
cfg->set_attr(config_name::agw_user, "your_agw_user");

// 3. 实例化 API 接口，需传入自定义的 api_callback 实现
api_interface* api = nullptr;
MyCallback my_cb;
int32_t ret = api_interface::create_instance(api, *cfg, &my_cb);

// 4. 释放不再使用的配置对象
api_config::destroy_config(cfg);
```

### 1.2 启动与登录流程
**注意点**：启动流程包含同步等待底层网关 (AGW) 的初始化。
1. 调用 `api->start()`：引擎将启动底层网络监听，并阻塞等待 98 柜台的网关认证完成。如果网关故障，这里会直接返回启动失败。
2. 调用 `api->login(LoginReq)`：传入具体的交易账户信息。这是一个**异步调用**。
3. 等待回调：在 `my_cb.on_login` 接收最终结果。**切勿在 `on_login` 返回成功之前发起任何交易请求**。

## 2. 核心业务接口的使用

### 2.1 委托与撤单
统一接口屏蔽了极速与综合柜台的差异。
- **买卖委托**: `api->order_insert(req)`
- **撤单**: `api->order_cancel(req)`
- **特性**: 调用立即返回 `LBAPI_OK` 表示本地排队成功。框架内部会**自动根据策略路由**，极速柜台优先，若极速不支持（如北交所品种）或发生故障，则自动静默降级给 98 柜台，业务方完全不需要编写 if-else 判断。

### 2.2 查询业务
查询类操作（如 `order_query`, `fund_query`, `position_query`）由 98 综合柜台全权处理。
- **调用方式**: 填入查询请求条件并调用 `api->fund_query(req)` 等接口。
- **异步应答**: 结果在回调如 `on_fund_query_ans` 中分批或一次性下发。由于查询较慢，请勿高频轮询。

## 3. 异步回调的避坑指南 (重要)

所有业务和链接状态通知都通过用户实现的 `api_callback` 推送。
1. **回调线程模型**：
   - 框架提供了两种回调模式。如果在配置中指定了**队列模式**，回调是在独立的后台线程执行的。
   - 如果是**直接模式**，回调则是在底层的网络收发 epoll 线程中同步执行。
2. **绝对禁止阻塞**：
   - 在直接模式下，千万不能在 `on_order_rtn` 或 `on_trade_rtn` 等回调函数中进行长时间的 IO 操作（如写同步文件、同步查库），这会导致整个底层的接收队列阻塞，严重影响行情和后续订单的处理，导致巨大的系统延迟。
3. **重复消息处理**：
   - 底层虽对极速网络增加了 `session_seq_no` 进行去重，但在极端情况下（如网络切换导致 session 失效）上层可能收到重复订单推送。推荐用户侧依据 `stream_seq` 辅以本地订单状态机进行幂等处理。

## 4. 异常处理与资源回收
- **自动重连与断线感知**：底层的物理网络断线、主备地址切换由框架自动闭环完成。业务侧会收到 `on_link_status` 状态变更通知。链接断开期间调用业务接口会返回错误码，需进行业务上的拦截或挂起。
- **优雅退出**：退出程序前，必须依序调用 `api->stop()` 停止所有线程与网络，然后调用 `api_interface::release_instance(api)` 回收实例内存，防止内存和文件句柄泄漏。
