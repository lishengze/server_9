### 2.2 读写方向（必须遵守）

- **写**：任务完成 → 先写 L4（work_log）→ 提炼进 L0/L1（必要时 L2/L3）→ 同步 `Prompt.md`。
- **读**：任务开始 → 先读 L0（自动加载）→ 按需读 L1 → 深入读 L3 → 查历史细节读 L4。

### 2.3 索引优先（重中之重）

- `MEMORY.md`（L0 与 L1 各一份）是"搜索引擎"，只放**导航表 + 核心结论 + 关键路径 + 准则**；细节一律放主题文件并在索引里引用。
- 新增主题文档后**必须**在两处 `MEMORY.md` 增加导航行，否则等于没沉淀。

### 2.4 文档写作规范（给 agent 看的文档，摘要自 `task_rule.md` §4.1）

1. **Context Pointer**：写清"材料是什么 + 什么时候该读它"（触发分支），而不是只给个路径。
2. **信息层次**：步骤内联、参考按需、细节放指针后（渐进披露）。
3. **引导词**：用预训练里已有的紧凑概念锚定行为（如 `tight`、`red`）。
4. **正向引导**：少写否定式禁令。
5. **单一事实来源**：同一含义只在一个权威位置；环境能查到的（`--help`/配置文件）不复述。
6. **每行检查相关性**：无 no-op 行，过时内容删除。

## 3. 工作规范体系（执行契约）

### 3.1 任务五阶段（每个任务必走）

| 阶段 | 必做动作 | 判定标准 |
|------|---------|---------|
| **1 接单分类** | 判定 编码 / 项目问答 / 通用问答 / 模糊任务；判断是否需 docker、编译、跨主机 | 类型明确，模糊先澄清 |
| **2 规划** | 拆子任务；**先检索 L0/L1/L4 有无现成答案**；写清验收标准 | 有任务清单 + 验收标准 |
| **3 执行验证** | 改动前读文件；精准编辑；**能编译就编译、能测就测、能部署就部署** | 有验证证据（非"看起来对"） |
| **4 复查** | 多轮复查，**本轮有修改就再开一轮**，直到某轮零修改；代码类按双轴审 | 某轮零修改 |
| **5 沉淀提交** | 写 work_log → 提炼知识 → 更新 `Prompt.md` → **显式询问用户是否提交 git** → 关 docker | 三份产出齐备 |

### 3.2 工作日志规则（`work_log/YYYYMMDD.md`）

- 每完成一次工作记录一条，**分块**写：时间 / 工作内容 / 结论 / 经验教训。
- **只追加，不覆盖**（内容可能来自其他主机/会话）。
- **日期以系统 `date` 命令为准**，跨午夜必须新建当天文件。
- 固定标题（`## 任务`、`### 工作内容`、`### 结论`、`### 经验教训`）是 `review_prepare.sh` 的聚合契约，改标题即断链路。

### 3.3 产出复查（双轴 + Fowler 坏味道）

- **Standards 轴**：是否符合仓库编码标准 + 12 种坏味道（Mysterious Name / Duplicated Code / Feature Envy / Data Clumps / Primitive Obsession / Repeated Switches / Shotgun Surgery / Divergent Change / Speculative Generality / Message Chains / Middle Man / Refused Bequest）。
- **Spec 轴**：是否忠实实现需求（别出现"代码漂亮但功能不对"）。
- 两轴**分开报告**，不合并排序；仓库已有标准优先于坏味道基线。

### 3.4 开发测试环境规则（原规则 + 本机现实，见 §7）

- 规则要求：功能开发测试在 **docker `otc`** 容器内 + **CMake 重新编译部署所有组件**（防旧库干扰），完成后**关闭 docker**。
- 本机现状：**无 docker、无 WSL 发行版**，`build.sh` 的宿主机分支会直接失败。要真正编译/回归，必须切到有 docker 的 Linux 主机或装 WSL+docker。

### 3.5 自检清单（收尾逐项打勾）

- [ ] 交付物完成并**验证**（不是"写完"）
- [ ] work_log 已追加（当天文件、固定标题）
- [ ] 经验教训已进知识库 + `Prompt.md` 已同步
- [ ] 多轮复查到零修改
- [ ] 已问用户是否提交 git
- [ ] docker 已关闭（若用过）

## 4. 自我进化体系（方法论内核）

### 4.1 三层记忆（模拟人脑）

| 记忆层 | 内容 | 落点 |
|--------|------|------|
| 工作记忆（短期） | 当前任务上下文、临时状态 | 对话上下文 + 任务清单 |
| 情景记忆（经历） | 每次做了什么、卡在哪、怎么解 | `work_log/YYYYMMDD.md` |
| 语义记忆（知识） | 提炼后的模式/架构/坑点/规则 | L0 + L1/L2 |
| 程序性记忆（技能） | 某类事的标准流程 | `Prompt.md` + 各执行规范 |

### 4.2 知识生命周期（6 步）

`捕获 → 验证（根因明确/可复现）→ 提炼（去噪/抽象/命名）→ 索引（主题文件 + MEMORY.md）→ 应用（检索复用）→ 保鲜（更新/合并/淘汰）`

**铁律**：未经证实的猜测不入库；宁精勿滥；一条经验要先过三问——**验证过吗？可复用吗？已有类似条目吗？**

### 4.3 三级提炼（经验 → 知识）

`work_log（详细、含过程）→ 去噪（删时间戳/个案）→ 抽象（现象→根因→解法，起个名字）→ 索引（归主题文件 + MEMORY.md + Prompt.md）`

### 4.4 三层学习

1. **任务即时学习**（刚需）：陌生/报错/复杂任务时实时检索补齐。
2. **短板靶向学习**（补弱）：按"高频踩坑 > 业务刚需 > 通用能力 > 拓展知识"排序。
3. **常态化新知学习**（前瞻）：定期学新框架/规范/工具。

学习 SOP 6 步：`问题定位 → 资料检索 → 知识消化 → 实操验证 → 技能固化 → 迭代复用`；学习钩子三问：**这是什么？怎么用/怎么配？坑在哪？**

### 4.5 四级复盘 + 五问 + 五转化

| 级别 | 频率 | 自动化程度 |
|------|------|-----------|
| 单任务即时复盘 | 每任务后 | ✅ 全自动（内嵌收尾） |
| 每日总结复盘 | 每日 | ⚠️ 半自动（脚本备数据 + 用户一句话触发） |
| 每周迭代复盘 | 每周 | ⚠️ 半自动 |
| 每月能力升级复盘 | 每月 | ⚠️ 半自动 |

- **核心五问**：达标吗/瑕疵？哪些高效可固化？哪些报错卡点、根因？下次怎么优化？要新增哪些 Skill/知识条目？
- **成果五转化**：高效经验→模板/Skill；报错踩坑→排障知识库（现象→根因→解法）；流程瑕疵→改 SOP；能力短板→靶向清单；优质案例→标杆案例库。
- **为什么不能全自动**：agent 是响应式，无 headless CLI，cron 只能跑脚本、叫不醒 agent。

### 4.6 量化指标（可度量地变强）

重复问题解决率、知识复用命中率、复查轮次、排障耗时、返工率。指标恶化 = 沉淀或规划环节有问题。

### 4.7 错误驱动学习（价值最高）

`记录报错原文 → 定位根因（看日志/复现，不猜） → 解法并验证 → 沉淀"现象→根因→解法"`。

## 5. 复盘运行手册（一句话触发即可）

用户说 **"进行daily复盘" / "weekly复盘" / "monthly复盘"**，我按下列 6 步执行：

1. **第零步（关键）**：主动跑 `bash task/review/review_prepare.sh <daily|weekly|monthly>` 刷新输入文件——**不依赖 cron 预生成**（当天更新过 work_log 后预生成文件会过时）。
   - 本机必须用 **Git bash**：`& 'C:\Program Files\Git\bin\bash.exe' -lc "cd /d/code/work/api_trunk && bash task/review/review_prepare.sh daily"`。
   - 为什么不能用 w64devkit 的 bash：它不支持数组，脚本第 63 行 `FILES=()` 直接语法报错退出（实测 exit=2），且其 `date` 无 `-d`。
2. 读 `task/review/<周期>_<日期>_input.md`，执行**核心五问**。
3. 执行**成果五转化**（找到落点，不是只写报告）。
4. 更新知识库 + `Prompt.md`（+ L0 的 `MEMORY.md`）。
5. 写报告 `task/review/<周期>_<日期>_report.md`（结构参照 `daily_2026-10-19_report.md`：五问 → 五转化 → 融合核查 → 结论）。
6. **知识库融合核查（必做，`task_rule.md` §8.4）**：逐条核对输入文件里的每条经验教训是否已在 L0/L1 有落点，缺失立即补写并在报告中记录核查结果——**核查不通过就不算复盘完成**。

## 6. NewAPI 项目知识地图（一页速览，细节见 `NewAPI_知识库.md`）

- **是什么**：面向客户的金融交易 API 客户端库（`trunk/NewAPI/`），对接 GONE（FPGA 极速）/ GW 个微（FTE 软件极速）/ Counter98（普通，查询唯一通道 + 降级目标）。
- **三层架构**：API 接口层（`api_interface`/`api_impl<TF,TE>`）→ 引擎层（`multi_socket_engine` 控制平面 / `single_socket_engine`、`tcpdirect_engine`、`idle_engine` 业务平面）→ 柜台层（`counter98` / `fpga_counter_direct` / `fpga_counter_gateway` / `gw_counter_direct`）+ 链接层（`aio_socket_link` / `tcpdir_link` / `link_timer_op`）+ 回调层（`callback_manager`）。
- **核心设计**：职责正交（Counter 懂协议、Engine 懂传输）、编译期模板多态（零虚函数）、无锁队列（`que_mth_buf`）、控制平面集中心跳、业务降级（极速失败自动落 98）。
- **五种实例化**：C1 gw+single / C2 gw+tcpdirect / C3 fpga_direct+single / C4 fpga_direct+tcpdirect / C5 fpga_gateway+idle。
- **性能基准（10000 TPS）**：GOne 平均 ~334–747ns / P50 ~120–245ns；FTE 平均 ~360–2172ns / P50 ~191–418ns。排序恒为 **GOne < GW**；FTE 最大瓶颈是**尾部延迟**（P95 曾达 GOne 的 9.4 倍）。
  - ⚠️ **口径警告**：`api_leave_time_ns` 记录点经历过"入队后 → send() 后 → send() 前"三次变更（§29/§30.8/§32），**跨章节的绝对值不可直接比大小**，只能比同章节内的排序；比较性能先确认口径一致。
- **必记铁律**：
  1. 队列"**预留长度 == 提交长度 == 读者消费长度**"三者必须一致（counter98 变长消息须先组包再精确预留）。
  2. 业务消息必须在 `aio_socket_link::deal_msg` 调 `pch->on_com_msg()`，否则 FTE 单向心跳下 15s 断链。
  3. `-DNO_DSE` 下 FTE 的 DSE 队列无消费者 → 队列满后 `push()` 忙等自旋（卡死）；修复=扩容 `FTE_DSE_FIFO_LEN` + NO_DSE 丢弃线程。
  4. 高 TPS 绑核必须绑**整个物理核 2 个 HT**（绑单核会饿死，TPS 骤降）。
  5. 性能测试前确保系统空闲（`tgw_simulator` 占 ~9 核会让 FTE 尾部延迟放大 10~40 倍）。
  6. FTE 撤单定位只用 `orig_clordno`；当前实现把 `OrderRtn.order_sys_no` 直接设为 clordno，客户端原样回传即可。
  7. 编译/部署/抓包的环境差异（`zsh -lc`、绝对路径 `--report`、`LANG=zh_CN.utf8` for svn）见 `NewAPI_知识库.md` §39.4 / `debug.md`。
