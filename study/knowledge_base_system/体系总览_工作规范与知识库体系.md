## 2. 知识库体系（L0~L4 分层）

### 2.1 分层与职责

| 层 | 位置 | 内容 | 读写特征 |
|----|------|------|---------|
| **L0 记忆索引** | 会话运行时记忆 `MEMORY.md`（本机 Linux 无 `~/.chat`，由 harness 注入；历史主机路径见 `MEMORY.md`「使用流程」第 4 条） | 主题导航 + 核心结论速查 + 关键路径 + 工作准则 | 最热、自动加载、**必须 <200 行**（超长被截断） |
| **L1 系统级知识库** | `study/knowledge_base_system/` | `MEMORY.md`（入口）/ `Prompt.md`（引导）/ `NewAPI_知识库.md`（主文档 §1~§41）/ 本文件（元层） | 主题化、按需读 |
| ~~**L2 业务级知识库**~~ | ~~`study/knowledge_base/`~~ → **已并入 L1，无独立目录** | 业务细节/出入参/新旧映射改放 `NewAPI_知识库.md` 新章节（§编号递增） | 按需读（同一份主文档） |
| **L3 深度专题** | `study/<主题>.md` | `counter.md` / `gw_counter.md` / `gone_counter.md` / `question.md` / `技术实现.md` / `数据流转.md` / `产品使用.md` | 深度、单主题 |
| **L4 原始日志** | `work_log/YYYYMMDD.md` | 每日任务流水 + 结论 + 经验教训 | 原始、**只追加不覆盖** |

### 2.2 读写方向（必须遵守）

- **写**：任务完成 → 先写 L4（work_log）→ 提炼进 L0/L1（必要时 L3）→ 同步 `Prompt.md`。
- **读**：任务开始 → 先读 L0（自动加载）→ 按需读 L1 → 深入读 L3 → 查历史细节读 L4。

### 2.3 索引优先（重中之重）

- `MEMORY.md`（L0 与 L1 各一份）是"搜索引擎"，只放**导航表 + 核心结论 + 关键路径 + 准则**；细节一律放主题文件并在索引里引用。
- 新增主题文档后**必须**在两处 `MEMORY.md` 增加导航行，否则等于没沉淀。
- **不再另建知识库目录**：新知识一律作为 `NewAPI_知识库.md` 的新章节（§编号递增），并同步 `Prompt.md` 加载指引 + `MEMORY.md` 导航。

### 2.4 文档写作规范（给 agent 看的文档，摘要自 `task_rule.md` §4.1）

1. **Context Pointer**：写清"材料是什么 + 什么时候该读它"（触发分支），而不是只给个路径。
2. **信息层次**：步骤内联、参考按需、细节放指针后（渐进披露）。
3. **引导词**：用预训练里已有的紧凑概念锚定行为（如 `tight`、`red`）。
4. **正向引导**：少写否定式禁令。
5. **单一事实来源**：同一含义只在一个权威位置；环境能查到的（`--help`/配置文件）不复述。
6. **每行检查相关性**：无 no-op 行，过时内容删除。

## 3. 工作规范体系（执行契约）

### 3.1 任务五阶段（每个任务必走）

| 阶段 | 必做动作 | 判定标准 |
|------|---------|---------|
| **1 接单分类** | 判定 编码 / 项目问答 / 通用问答 / 模糊任务；判断是否需 docker、编译、跨主机 | 类型明确，模糊先澄清 |
| **2 规划** | 拆子任务；**先检索 L0/L1/L4 有无现成答案**；写清验收标准 | 有任务清单 + 验收标准 |
| **3 执行验证** | 改动前读文件；精准编辑；**能编译就编译、能测就测、能部署就部署** | 有验证证据（非"看起来对"） |
| **4 复查** | 按 `task_rule.md` §3 **台账制**：一轮 = 本轮全量产出 × 六维度全检 + 验证证据 + 台账；任一处改动即重开**全量**复查；代码类另加双轴审 | **末轮零修改** + 台账已填（`task_rule.md` §11.3） |
| **5 沉淀提交** | 写 work_log → 提炼知识 → 更新 `Prompt.md` → **显式询问用户是否提交 git** → 关 docker | 三份产出齐备 |

### 3.2 工作日志规则（`work_log/YYYYMMDD.md`）

- 每完成一次工作记录一条，**分块**写：时间 / 工作内容 / 结论 / 经验教训。
- **只追加，不覆盖**（内容可能来自其他主机/会话）。
- **日期以系统 `date` 命令为准**（不采用对话上下文里的日期），跨午夜必须新建当天文件，**不得续写昨天**。
- 固定标题（`## 任务`、`### 工作内容`、`### 结论`、`### 经验教训`）是 `review_prepare.sh` 的聚合契约（`task_rule.md` §11.1），改标题即断链路；**经验教训小节里不要出现「待办/遗留问题」字样**，否则脚本会把后续行误抓进第三节（2026-11-05 实测踩到）。

### 3.3 产出复查（台账制：六维度 × 多轮 + 双轴 + Fowler）

**规则原文见 `task_rule.md` §3，这里只记可执行口径。** 适用范围无豁免：代码 / SQL / 测试 / 文档 / 配置 / 脚本都算。

| 要点 | 口径 |
|------|------|
| **一轮的定义** | 本轮**全部**产出 × 六维度**逐条全检** + 有验证证据 + 留一条台账；只查"最后改的那几行"不算一轮 |
| **六维度** | ①需求符合 ②正确与边界 ③一致性 ④引用可达 ⑤规范与风格 ⑥可验证性 |
| **零修改判定** | 六维度全勾 + 无待改项（不是"下轮再说"）+ 证据齐全 |
| **重开规则** | **任一处被改动 → 本轮作废，重开全量复查**（不是只复查改动点） |
| **收工条件** | 出现**一轮零改动**；收敛保护：连续 3 轮反复改同一处 → 回阶段2 重新规划 |
| **记录义务** | 交付时能回答"几轮、每轮查了什么、末轮是否零改动"——台账模板 `task_rule.md` §11.3 |

- **④ 引用可达** 是本仓库最高频的翻车点：路径 / 文件名 / 章节号 / 符号必须真实存在，用 `rg`（本机缺则 `grep -rn`）全局核对，**不凭记忆**。
- **⑤ 规范与风格** = 仓库标准优先，其次 Fowler 12 种坏味道；代码类另按**双轴**分开报告：Standards 轴（编码标准 + 坏味道）、Spec 轴（是否忠实实现需求），不合并排序。

### 3.4 开发测试环境规则（原规则 + 本机现实，见 §7）

- 规则要求：功能开发测试在 **docker `otc`** 容器内 + **CMake 重新编译部署所有组件**（防旧库干扰），完成后**关闭 docker**。
- 本机现状（2026-11-05 复核）：**Linux + docker `otc` 在运行**，`./build.sh Release` 直接可用 → 编译/回归/压测不受限（详见 §7.1）。仅历史 Windows 主机无法编译。

### 3.5 自检清单（收尾逐项打勾）

- [ ] 交付物完成并**验证**（有编译/测试/命令输出为证）
- [ ] work_log 已追加（当天文件、固定标题）
- [ ] 经验教训已进知识库 + `Prompt.md` 已同步
- [ ] **末轮零修改** + 六维度全勾 + 台账已填（`task_rule.md` §11.3）
- [ ] 引用/路径/章节号已用 `rg`（本机缺则 `grep -rn`）全局核对，非凭记忆
- [ ] 改过规范则已跑 `bash task/sync_rules.sh`（`-c` 校验通过）
- [ ] 已问用户是否提交 git
- [ ] docker 已关闭（若用过）

### 3.6 规范的单一事实来源（`task/sync_rules.sh`）

- **权威源唯一**：只改 `task/task_rule.md`；`.chat/rules/project_rules.md` 是**生成物**（面向所有 agent/会话），禁止手改。
- **同步姿势**：改完规范化 → `bash task/sync_rules.sh` 生成副本 → `bash task/sync_rules.sh -c` 校验（退出码 0 = 一致）。
- **为什么用脚本**：副本不入 git（`.chat/.gitignore` 为 `*`），历史上两份手写已漂移（副本曾缺 §6/§8.4、多出 §7.4）；"记得同步"不可靠，"跑一条命令"才可靠。
- **同源提示**：`memory/self_evolution.md`、`task/task_prompt.md`、`task/review/README.md` 的规则引用都用「章名 + §号」；改章节编号后 `grep -rn "§" task/ memory/` 全局核对一次。

## 4. 自我进化体系（方法论内核）

### 4.1 三层记忆（模拟人脑）

| 记忆层 | 内容 | 落点 |
|--------|------|------|
| 工作记忆（短期） | 当前任务上下文、临时状态 | 对话上下文 + 任务清单 |
| 情景记忆（经历） | 每次做了什么、卡在哪、怎么解 | `work_log/YYYYMMDD.md` |
| 语义记忆（知识） | 提炼后的模式/架构/坑点/规则 | L0 + L1/L2 |
| 程序性记忆（技能） | 某类事的标准流程 | `Prompt.md` + 各执行规范 |

### 4.2 知识生命周期（6 步）

`捕获 → 验证（根因明确/可复现）→ 提炼（去噪/抽象/命名）→ 索引（主题文件 + MEMORY.md）→ 应用（检索复用）→ 保鲜（更新/合并/淘汰）`

**铁律**：未经证实的猜测不入库；宁精勿滥；一条经验要先过三问——**验证过吗？可复用吗？已有类似条目吗？**

### 4.3 三级提炼（经验 → 知识）

`work_log（详细、含过程）→ 去噪（删时间戳/个案）→ 抽象（现象→根因→解法，起个名字）→ 索引（归主题文件 + MEMORY.md + Prompt.md）`

### 4.4 三层学习

1. **任务即时学习**（刚需）：陌生/报错/复杂任务时实时检索补齐。
2. **短板靶向学习**（补弱）：按"高频踩坑 > 业务刚需 > 通用能力 > 拓展知识"排序。
3. **常态化新知学习**（前瞻）：定期学新框架/规范/工具。

学习 SOP 6 步：`问题定位 → 资料检索 → 知识消化 → 实操验证 → 技能固化 → 迭代复用`；学习钩子三问：**这是什么？怎么用/怎么配？坑在哪？**

### 4.5 四级复盘 + 五问 + 五转化

| 级别 | 频率 | 自动化程度 |
|------|------|-----------|
| 单任务即时复盘 | 每任务后 | ✅ 全自动（内嵌收尾） |
| 每日总结复盘 | 每日 | ⚠️ 半自动（脚本备数据 + 用户一句话触发） |
| 每周迭代复盘 | 每周 | ⚠️ 半自动 |
| 每月能力升级复盘 | 每月 | ⚠️ 半自动 |

- **核心五问**：达标吗/瑕疵？哪些高效可固化？哪些报错卡点、根因？下次怎么优化？要新增哪些 Skill/知识条目？
- **成果五转化**：高效经验→模板/Skill；报错踩坑→排障知识库（现象→根因→解法）；流程瑕疵→改 SOP；能力短板→靶向清单；优质案例→标杆案例库。
- **为什么不能全自动**：agent 是响应式，无 headless CLI，cron 只能跑脚本、叫不醒 agent。
- **执行细节**：自动化边界表 + 三步半自动流程 + cron 示例见 `task_rule.md` §8.5；脚本见 `task/review/review_prepare.sh`。

### 4.6 量化指标（可度量地变强）

重复问题解决率、知识复用命中率、复查轮次、排障耗时、返工率。指标恶化 = 沉淀或规划环节有问题。

### 4.7 错误驱动学习（价值最高）

`记录报错原文 → 定位根因（看日志/复现，不猜） → 解法并验证 → 沉淀"现象→根因→解法"`。

**执行版本＝Bug 诊断六阶段**（`task_rule.md` §6.1）：①复现（建最小可重跑用例）②观察（只收集证据，不改代码）③假设（可证伪的单一根因）④验证（一次只验一个变量）⑤修复（只改根因处）⑥回归（原用例 + 新增覆盖该 bug 的用例）。铁律：**先建反馈回路，再提假设，最后才改代码**。

## 5. 复盘运行手册（一句话触发即可）

用户说 **"进行daily复盘" / "weekly复盘" / "monthly复盘"**，我按下列 6 步执行：

1. **第零步（关键）**：主动跑 `bash task/review/review_prepare.sh <daily|weekly|monthly>` 刷新输入文件——**不依赖 cron 预生成**（当天更新过 work_log 后预生成文件会过时）。
   - 本机（Linux）直接 `bash task/review/review_prepare.sh daily` 即可（GNU date + 数组均支持，2026-11-05 实测通过）。
   - 历史（Windows 主机）：必须用 Git bash（`C:\Program Files\Git\bin\bash.exe`）；w64devkit 的 bash 不支持数组（`FILES=()` 报错 exit=2）且 `date` 无 `-d`。2. 读 `task/review/<周期>_<日期>_input.md`，执行**核心五问**。
3. 执行**成果五转化**（找到落点，不是只写报告）。
4. 更新知识库 + `Prompt.md`（+ L0 的 `MEMORY.md`）。
5. 写报告 `task/review/<周期>_<日期>_report.md`（结构参照 `daily_2026-10-19_report.md`：五问 → 五转化 → 融合核查 → 结论）。
6. **知识库融合核查（必做，`task_rule.md` §8.4）**：逐条核对输入文件里的每条经验教训是否已在 L0/L1 有落点，缺失立即补写并在报告中记录核查结果——**核查不通过就不算复盘完成**。

## 6. NewAPI 项目知识地图（一页速览，细节见 `NewAPI_知识库.md`）

- **是什么**：面向客户的金融交易 API 客户端库（`trunk/NewAPI/`），对接 GONE（FPGA 极速）/ GW 个微（FTE 软件极速）/ Counter98（普通，查询唯一通道 + 降级目标）。
- **三层架构**：API 接口层（`api_interface`/`api_impl<TF,TE>`）→ 引擎层（`multi_socket_engine` 控制平面 / `single_socket_engine`、`tcpdirect_engine`、`idle_engine` 业务平面）→ 柜台层（`counter98` / `fpga_counter_direct` / `fpga_counter_gateway` / `gw_counter_direct`）+ 链接层（`aio_socket_link` / `tcpdir_link` / `link_timer_op`）+ 回调层（`callback_manager`）。
- **核心设计**：职责正交（Counter 懂协议、Engine 懂传输）、编译期模板多态（零虚函数）、无锁队列（`que_mth_buf`）、控制平面集中心跳、业务降级（极速失败自动落 98）。
- **五种实例化**：C1 gw+single / C2 gw+tcpdirect / C3 fpga_direct+single / C4 fpga_direct+tcpdirect / C5 fpga_gateway+idle。
- **性能基准（10000 TPS）**：GOne 平均 ~334–747ns / P50 ~120–245ns；FTE 平均 ~360–2172ns / P50 ~191–418ns。排序恒为 **GOne < GW**；FTE 最大瓶颈是**尾部延迟**（P95 曾达 GOne 的 9.4 倍）。
  - ⚠️ **口径警告**：`api_leave_time_ns` 记录点经历过"入队后 → send() 后 → send() 前"三次变更（§29/§30.8/§32），**跨章节的绝对值不可直接比大小**，只能比同章节内的排序；比较性能先确认口径一致。
- **目录现状（2026-11-05 核对）**：主实现 `trunk/NewAPI/gone/api/`（编译入口 `gone/api/CMakeLists.txt`）；`gone/api-compare/` 是框架开发者转存版，**未接入 CMake、不编译**，只作对照取长（分析见 `task/api_dev/api_compare.md`）；mock 四目标（client / 98_counter / gone_counter / perf_client）。路径修正表与代码树见 `NewAPI_知识库.md` §42。
- **必记铁律**：
  1. 队列"**预留长度 == 提交长度 == 读者消费长度**"三者必须一致（counter98 变长消息须先组包再精确预留）。
  2. 业务消息必须在 `aio_socket_link::deal_msg` 调 `pch->on_com_msg()`，否则 FTE 单向心跳下 15s 断链。
  3. `-DNO_DSE` 下 FTE 的 DSE 队列无消费者 → 队列满后 `push()` 忙等自旋（卡死）；修复=扩容 `FTE_DSE_FIFO_LEN` + NO_DSE 丢弃线程。
  4. 高 TPS 绑核必须绑**整个物理核 2 个 HT**（绑单核会饿死，TPS 骤降）。
  5. 性能测试前确保系统空闲（`tgw_simulator` 占 ~9 核会让 FTE 尾部延迟放大 10~40 倍）。
  6. FTE 撤单定位只用 `orig_clordno`；当前实现把 `OrderRtn.order_sys_no` 直接设为 clordno，客户端原样回传即可。
  7. 编译/部署/抓包的环境差异（`zsh -lc`、绝对路径 `--report`、`LANG=zh_CN.utf8` for svn）见 `NewAPI_知识库.md` §39.4 / `debug.md`。

### 7.2 Git 推送（先直连 SSH，不通再走代理）

| 路径 | 结果 |
|------|------|
| 直连 `github.com:22` / `:443` | ❌ 超时 |
| HTTPS 经代理 `172.16.0.11:3128` | ✅ 200，但会**成片 502**（实测连续约 7 分钟、20 次探活全 502 后恢复） |
| SSH 经代理（`connect.exe -H/-T`） | ❌ 隧道 200 但收不到 SSH banner → 代理只放行 HTTPS |

**做法**：`origin` 是 SSH 地址，推送改走 HTTPS URL + 命令级代理（不写配置）。一条命令即可（含探活重试 + 推后校验）：

```powershell
pwsh -NoProfile -File task/tool/git_push_proxy.ps1
```

**Linux 主机：优先直连 SSH**（2026-11-05 实测成功，无需代理）：

```bash
ssh -T git@github.com            # 返回 "Hi lishengze!" 即可直推
git push origin master           # 实测 143d763..49ec5b7 成功
```

**代理路径的等价命令**（直连不通时，2026-11-05 代理探活 200）：

```bash
curl -sS -m 8 -x http://172.16.0.11:3128 -o /dev/null -w '%{http_code}\n' https://github.com/   # 探活需 200
git -c http.proxy=http://172.16.0.11:3128 push https://github.com/lishengze/server_9.git master
```

**推完必须取消代理**（`-c` 天然无残留：Linux `git config --list | grep proxy`、Windows `git config --list | Select-String proxy` 均应无输出）。完整规则见 `task/task_rule.md` §13。
