# 核心原则
1. **严格遵从规划**：规则的数量、模块划分、触发方式（是自动替换还是仅提示），必须严格以 @docs/lb_common_plan.md 中的要求为准，不要自行发挥增删模块。
2. **精准拦截**：对于规划中明确要求“拦截原生 API”的规则，必须写出高质量的正则表达式（如拦截 std::mutex、socket(、fread 等）。
3. **安全第一**：对于有前置条件、多场景选型的 API（如锁的选择、内存池的选择），规则中只能使用 action 进行提示，**绝对不能使用 replace 进行自动替换**。

# 格式要求
请为规划中的每一个模块生成一个独立的规则文件，使用 Continue 推荐的 .mdc 格式（或带 YAML 头的 Markdown），格式模板如下：
1) 在文件开头注释说明这是一个规则文件和针对哪个模块的
2) 每条规则生成一个独立的 Markdown 文件，使用 Continue 推荐的规则格式：
   - YAML 前置字段：name、description、globs（如适用）、regex（如适用）、alwaysApply（明确写 true/false）；
   - 正文部分用 Markdown 写清楚：
     - 本规则要达成的目标；
     - 需要拦截/匹配的 API/模式；
     - 替换/改写建议（如果适合自动替换，给出明确“替换为”示例；如果不适合，写明“仅提示”）；
     - 注意事项/坑（对齐、副作用等）。
3) 文件名按模块命名，比如：线程安全的锁机制 lbcommon-lock.md
4) 对“拦截原生 API”的规则，优先使用 regex（比如 std::mutex、pthread_mutex_t、socket(、bind(、send(、recv( 等），并在 description 中写清楚拦截意图。
5) 对“纯风格/选型提示”的规则，用 alwaysApply: true。

# ⚠️ 核心认知前提（极其重要）
在我们的配置体系中，**微观 API 拦截已经由各个模块的 Rules 文件全面接管了**（比如把原生 socket 换成 sock_utils，把原生 mutex 换成 cmutex 等）。
因此，你现在要写的这个 Prompt，**绝对不能再去罗列具体的 API 替换规则、基础类型命名细节或微观的组件选型 if-else**，那些是 Rules 干的事。

# 你的任务：塑造“基于 lb_common 编程的心智模型”
这个 Prompt 的受众是“即将开始设计业务代码的 AI”。你需要让它像一个熟练掌握 lb_common 的资深架构师一样思考。请严格按以下四个维度来写：

## 1. 领域边界与优先级声明（确立 lb_common 的统治领域）
开篇必须明确 lb_common 与 C++ 标准库的“领地边界”，要求 AI 严格遵守以下分层原则：
- **底层/性能敏感领域（lb_common 绝对优先）**：当业务需求涉及网络通信、多线程并发与同步、底层内存分配与管理、高性能数据管道（队列/环形缓冲区）、时间与休眠控制时，lb_common 是**唯一合法的底层实现**。在这些领域，严禁 AI 直接调用 POSIX 原生 API（如 socket/pthread）或重新造轮子，必须基于 lb_common 提供的模型（如 aio_tcp/udp_ch/que_mth_buf/fix_pool 等）进行拼装设计。
- **通用业务逻辑领域（标准库合法）**：当业务需求处于普通的数据处理、配置管理、字符串常规拼接、非热路径的键值存储等场景时，允许且鼓励使用现代 C++ 标准库（如 std::string, std::vector, std::map, std::shared_ptr 等），以保持业务代码的简洁性与可读性。

## 2. 生态协同声明（告知 AI 它的战友是谁）
明确告诉 AI，它不是孤军奋战，它必须依赖以下生态，并说明如何配合：
- **依赖 Rules**：告诉 AI，“当你试图在性能敏感领域使用原生底层 API 时，当前的规则系统会自动纠错或提示你，请听从 Rules 的指示进行微观修改。”（解决类似“内存池不能硬拦，需要 Prompt 赋予性能意识去配合 Rules 提示”的问题）。
- **依赖架构文档**：告诉 AI，“遇到复杂的模板参数配置、不熟悉的组件内部机制时，不要凭空猜测，必须主动查阅 @docs/lb_common_arch.md 获取真相。”

## 3. 宏观架构范式（最核心的部分！）
这是 Prompt 的灵魂。不要写“有什么组件”，要写“遇到典型业务，应该怎么组装组件”。
请从架构文档中提取 2-3 种典型的业务架构范式，作为 AI 设计代码的“模板”。例如：
- **网络服务器范式**：当需求是处理网络请求时，标准架构应是 `mthread(线程池) -> tcp_ch/udp_ch(通道管理) -> aio_tcp/aio_udp(异步收发) -> que_mth_buf(分发队列) -> 业务逻辑`。
- **多线程流水线范式**：当需求是生产者-消费者模型时，标准架构应是 `simple_thread -> que_mth_buf(解耦) -> fix_pool/dync_pool(节点池)`。
- **跨进程共享范式**：当需求涉及进程间通信时，强调生命周期的管理（shmem_pool + que_proc_buf）。

## 4. 隐式设计哲学（补充 Rules 无法触及的软实力）
提炼文档中的设计哲学，指导 AI 写出“好看、好维护”的代码：
- 比如文档提到的“三阶段接收模型（recv_msg -> deal_msg -> cmt_deal）”，告诉 AI 在继承或重写网络回调时，必须遵守这个生命周期。
- 比如文档提到的“RAII 锁守卫”，告诉 AI 在业务代码中体现这种资源管理意识。
