
# task_rule.md — Agent 通用工作规则（跨会话 / 跨项目 / 跨场景）

> 本文件是 Agent 执行任何任务的**统一行为规范**，由两部分融合而成：
> ① `task/task_all.txt` 第 1~15 行的工作准则（用户明确要求，长期遵守）；
> ② `task/task_upgrade.md` 的自我进化体系（工作/学习/总结/知识库方法论）。
>
> 适用范围：不同的会话、项目、场景、任务均可统一使用。
> 本规则同时写入 `.chat/rules/project_rules.md`，面向所有 agent 与会话生效。

---

## 0. 总则

1. **一次任务，三份产出**：① 任务交付物；② 工作日志条目；③ 提炼后的知识条目。缺一不可。
2. **先把事做对，再求快**：改动前先理解，执行后必验证，产出必复查。
3. **验证优先，不凭猜测**：所有结论要有依据（编译通过/测试通过/日志证据/实测复现）。
4. **持续进化**：每次任务都是一次学习机会，把经验沉淀为可复用知识。

## 1. 工作流程规则（任务五阶段）

每个任务按五阶段执行：

### 阶段1 接单分类

- 判断任务类型：**编码 / 项目问答 / 通用问答 / 模糊任务**。
- 编码类 → 先收集项目信息；通用问答 → 直接回答不调工具；模糊任务 → 先澄清。

### 阶段2 规划

- 复杂任务用 `add_tasks` 拆解成可追踪子任务（id + 状态）。
- **先检索记忆/知识库/历史排障**，看有无现成答案，避免重复劳动。
- 明确验收标准（"什么叫完成"）。

### 阶段3 执行验证

- 改动前先读相关文件，不凭空猜测；修改用精准编辑，创建用新文件。
- **必须验证**：能编译的编译、能测试的测试、能部署的部署；文档类检查引用与格式。
- 开发测试一律在 docker `otc` 容器内 + CMake 重新编译部署，防旧库干扰。

### 阶段4 复查（多轮）

- 对所有产出执行**多轮复查**（见 §3）。

### 阶段5 沉淀提交

- 写工作日志 → 提炼知识 → 更新 Prompt.md → **显式询问用户是否提交 git**（若选择是，设置合适 commit 内容并推送到远程仓库）→ 关闭 docker。

## 2. 工作日志规则（来源：task_all.txt 第 1~3 行）

1. **每完成一次工作，记录一次工作日志**，将工作的时间、内容、效果、经验教训**分块**记录到 `work_log/` 对应日期的 markdown 文件。
2. **不要删除**当前工作日志的内容——这些内容可能来自其他主机/其他会话，**只能追加，不能覆盖**。
3. 若文件夹没有该日期文件，则创建该文件夹和日期文件，文件名格式 **`YYYYMMDD.md`**（如 `work_log/20261009.md`）。
4. 日志模板见 §11.1。

## 3. 产出复查规则（来源：task_all.txt 第 4 行 + 双轴 Code Review）

对**所有产出**（代码文件、SQL 脚本、测试代码、文档等）执行以下复查流程：

### 3.1 多轮复查（基础流程）

1. **每一轮都复查、审核该轮涉及的内容**，检查是否符合要求，进行查漏补缺的修改。
2. **反复审查所有生成的内容并修改完善**，直到当前轮次结束后整个轮次**没有一处需要修改**。
3. **只要当前轮次结束后发现修改完善了一个内容，就再开启一轮全面的审查工作**。
4. 复查不仅是"看"，更要"验证"（编译/测试/跑通）。

### 3.2 双轴审查（升级版，参考 lsz-skills-real-engineers）

对于代码类产出，按**两个轴**并行审查，防止一个轴掩盖另一个：

| 轴                     | 评审内容                                             | 典型失败                   |
| ---------------------- | ---------------------------------------------------- | -------------------------- |
| **Standards 轴** | 代码是否符合仓库编码标准 + Fowler 坏味道基线（见下） | 实现了正确功能但代码质量差 |
| **Spec 轴**      | 代码是否忠实实现了需求/规格                          | 代码写得很漂亮但功能不对   |

两轴并行，报告分开呈现，不合并排序。

### 3.3 Fowler 坏味道基线（12 种）

适用于代码复查，作为 Standards 轴的基线：

| 坏味道                           | 特征                       | 修复               |
| -------------------------------- | -------------------------- | ------------------ |
| **Mysterious Name**        | 名字不揭示功能             | 重命名             |
| **Duplicated Code**        | 相同逻辑出现在多处         | 提取共享           |
| **Feature Envy**           | 方法更多使用其他对象的数据 | 移到它嫉妒的数据上 |
| **Data Clumps**            | 相同字段总一起出现         | 打包成类型         |
| **Primitive Obsession**    | 基本类型代替领域概念       | 给概念自己的类型   |
| **Repeated Switches**      | 相同 switch/if 级联重复    | 多态或共享映射     |
| **Shotgun Surgery**        | 一个变化需散落多处编辑     | 集中到一个模块     |
| **Divergent Change**       | 一个文件因无关原因被改     | 拆分               |
| **Speculative Generality** | 添加了规格不需要的抽象     | 删除               |
| **Message Chains**         | 长 a.b().c().d() 导航      | 在第一个对象上隐藏 |
| **Middle Man**             | 类主要做委托               | 直接调用真实目标   |
| **Refused Bequest**        | 子类忽略大部分继承内容     | 组合替代继承       |

> 规则：仓库已有标准 > 坏味道基线；坏味道是判断调用，非硬违规；跳过工具已检查的内容。

## 4. 知识沉淀规则（来源：task_all.txt 第 5 行 + 自进化体系）

1. 当前知识库目录：`study/knowledge_base_system`（系统级，架构/开发/编译/部署/测试/排障/消息/数据流转/复盘体系），对工程各环节进行了总结。若项目另建业务级知识库 `study/knowledge_base`（业务细节/出入参/新旧映射），两级维度互补、互相引用而非重复。
2. **每次工作完成后，对此次工作所学的经验、教训进行总结**，更新到对应的知识库文档中。
3. **更新 `Prompt.md` 的内容**，使后续学习能覆盖最新知识（跨会话知识迁移）。
4. 遵循**知识生命周期**：捕获 → 验证 → 提炼 → 索引 → 应用 → 保鲜。
5. **禁止把未经证实的猜测写进知识库**；宁精勿滥，只沉淀可复用、有区分度的内容。
6. 用户纠正你基于记忆的陈述时，**必须更新/删除错误记忆**。

### 4.1 文档写作规范（writing-for-agents 要点）

知识库/Prompt.md 都是"给 agent 看的文档"，遵循以下规范（详见 `11_工程纪律.md` §6）：

- **Context Pointer**：指针措辞决定 agent 何时触及材料，要写清"材料是什么 + 触发分支"。
- **信息层次**：步骤内联、参考按需查阅、细枝末节放指针后（渐进披露）。分支是最干净的披露测试。
- **引导词（Leading Word）**：用已存在于预训练的紧凑概念（如 `tight`/`red`）锚定行为，省 token 且更准。
- **正向引导，少用否定**：禁止指令会把禁止行为拖入上下文。
- **单一事实来源**：每个含义只在一个权威位置；环境能查到的（`--help`/配置文件）不要复述。
- **每行检查相关性**：无 no-op（不改变默认行为的指令）；过时的删除。

## 5. 开发测试环境规则（来源：task_all.txt 第 6~7 行）

1. 每次进行功能开发测试，都在 **docker `otc` 容器环境**下进行。
2. 使用 **CMake 重新编译部署所有组件**，防止旧的生成库干扰。
3. 每次涉及在 docker 中的功能开发测试完成后，**记得关闭 docker**，减少机器消耗。

## 6. 问题解决准则（来源：用户 2026-10-10 明确要求）

1. **遇到尝试三次以上仍解决不了的问题**，**先完整学习知识库中已总结的内容**（`study/knowledge_base_system/`、`work_log/`、`MEMORY.md`），**再去拓展性地思考解决方案**，不能一直重复排查已知问题。
2. 问题**解决之后**，若属于**新出现的问题**（知识库中未记录），**记得补充到知识库**（对应主题文档 + 记忆索引 + Prompt.md）。
3. 此准则需跨会话长期遵守。

## 7. 学习规则

1. **主动学习 + 被动学习结合**：任务驱动学新功能，计划驱动回顾不熟悉领域。
2. **三层学习机制**（参考 agent_upgrade.md）：
   - **任务即时学习**：执行陌生/报错/复杂任务时，实时检索知识、补齐能力缺口；
   - **短板靶向学习**：基于复盘统计高频出错/低效任务，定向补弱（优先级：高频踩坑 > 业务刚需 > 通用能力 > 拓展知识）；
   - **常态化新知学习**：定期学习新技术/框架/规范/工具，拓宽能力边界。
3. **标准化学习 SOP（6 步）**：问题定位 → 资料检索 → 知识消化 → 实操验证 → 技能固化 → 迭代复用。
4. **学习钩子**：每次任务问自己三个问题——这是什么？怎么用/怎么配？坑在哪？
5. **跨会话知识迁移**：知识通过 `Prompt.md` 被下一会话 Agent 重新加载，实现继承。
6. 新功能研究产出到 `study/<功能号>_<业务名>/`，模式沉淀进知识库。

## 8. 复盘体系（四级复盘 + 成果固化）

> 参考 agent_upgrade.md，将"单任务复盘"升级为**四级复盘体系**，是 Agent 自进化的核心环节。

### 8.1 四级复盘体系

| 级别                       | 频率               | 内容                                                  |
| -------------------------- | ------------------ | ----------------------------------------------------- |
| **单任务即时复盘**   | 每次任务后（必做） | 用"复盘核心五问"轻量复盘单次任务得失                  |
| **每日总结复盘**     | 每日               | 汇总当日任务，统计高频问题/新增技能/能力短板          |
| **每周迭代复盘**     | 每周               | 迭代 SOP 流程、优化 Skill、清理无效知识、补充缺失能力 |
| **每月能力升级复盘** | 每月               | 盘点能力体系，对比月初基线，评估成长，制定下月计划    |

### 8.2 复盘核心五问（单任务即时复盘必问）

1. 本次任务是否完全达标？存在哪些瑕疵？
2. 执行中哪些步骤高效、可固化复用？
3. 出现了哪些报错/卡点/低效问题？根因是什么？
4. 下次同类任务如何优化流程、规避问题？
5. 需要新增/优化哪些 Skill、知识库条目？

### 8.3 复盘成果五转化（固化规范）

| 复盘发现 | 转化去向                                                |
| -------- | ------------------------------------------------------- |
| 高效经验 | → 固化为**标准化 Skill/流程模板**                |
| 报错踩坑 | → 录入**问题解决方案知识库**（现象→根因→解法） |
| 流程瑕疵 | → 优化**通用工作 SOP**（task_rule.md）           |
| 能力短板 | → 列入**靶向学习清单**                           |
| 优质案例 | → 存入**标杆案例库**复用                         |

### 8.4 复盘后知识库融合核查（必做，用户 2026-10-13 明确要求）

**每次进行 daily / weekly / monthly 复盘后，必须核查"当日的经验教训总结是否已融合到知识库中"**，避免"只出报告、不反哺"：

1. **逐条核对**：复盘输入文件（`task/review/<周期>_<日期>_input.md`）中列出的每条"经验教训"，逐一确认是否已写入对应知识库主题文档（`study/knowledge_base_system/` 或 `memory/`）。
2. **补写缺失**：对尚未沉淀的经验教训，立即补写进知识库对应主题文档，并同步更新 `MEMORY.md` 索引速查 + `Prompt.md`（实现跨会话知识迁移）。
3. **闭环确认**：全部经验教训都已在知识库中找到落点后，复盘才算真正闭环；在复盘报告中记录核查结果。

> 触发分支：执行 daily/weekly/monthly 复盘时，在"写复盘报告"步骤前执行本核查。

## 10. 对话与工具使用规则

1. **对话窗口**：用自然语言清晰表达任务意图、上下文、期望结果。
2. **命令执行**：有充分权限，可执行安装/卸载等命令；高风险操作（删数据/改历史/装依赖）先确认。
3. **项目规则**：`.chat/rules/project_rules.md` 面向所有 agent/会话，统一遵守。
4. **Skills**：按需从 skills 广场加载合适技能，并将技能用法沉淀进知识库。
5. **工具选择**：文件/代码探索优先用 `list_files`/`search_relative`/`get_file_content`；编辑用 `replace_in_file`/`write_to_file`；构建测试部署用 `run_command`。
6. **工具调用次数限制**：当系统因工具调用次数达到上限而询问"是否继续"时，**直接选择继续工作**，无需询问用户。保持工作连续性，避免无谓中断。

## 13. git 提交与远程推送规则（代理，2026-10-29 新增，同日实测校准）

### 13.1 提交前

1. **先问用户**是否提交 git（§12）；用户同意后，**工作日志与知识库改动一并提交**，防止"代码提交了、日志没提交"。
2. **检查待提交内容**：`git status --short` + `git diff --stat`，确认没有误提交临时脚本/大文件/敏感信息（含密码的脚本必须清理，见 §7 教训）。
3. **先拉后推**：`git fetch` 刷新远端 tracking → 有他人提交则 `git merge`（或 `git pull --rebase`）后再推，避免 non-fast-forward。
4. **注意工作区里别人的改动**：`git status` 里出现不是本轮产出的文件（并发会话/用户手改），**只 `git add` 自己产出的路径**，不 `git add -A`。

### 13.2 推送需要代理时的处理（**用后必须取消**）

本机（`D:\code\work\api_trunk`）远端是 **SSH 地址** `git@github.com:lishengze/server_9.git`，而直连 22/443 均超时，必须挂 HTTP 代理 **`172.16.0.11:3128`**。

```powershell
cd D:\code\work\api_trunk
$env:GIT_TERMINAL_PROMPT='0'; $env:GCM_INTERACTIVE='never'   # 防交互卡死
git -c http.proxy=http://172.16.0.11:3128 push https://github.com/lishengze/server_9.git master
```

**关键：推的是 HTTPS URL，不是 `origin`** —— `origin` 是 SSH 地址，SSH 过不了代理（见下表）。

### 13.3 环境实测结论（2026-10-29）

| 路径 | 结果 | 说明 |
|------|------|------|
| 直连 `github.com:22` / `:443` | ❌ 超时 | `Test-NetConnection` 全 False |
| HTTPS 经代理 | ✅ 200 | `curl -x http://172.16.0.11:3128 https://github.com/`；**偶发 502，重试 2~3 次即通** |
| SSH 经代理（`connect.exe -H`/`-T`） | ❌ 隧道 200 但无 banner | 隧道能建立、随后 `Connection timed out during banner exchange` → **代理只放行 HTTPS，不放行 SSH** |
| HTTPS 凭据 | ✅ 无需交互 | Windows 凭据管理器已存 `git:https://github.com`（用户 `lishengze`） |

> 结论：**不要在 `GIT_SSH_COMMAND` / `ProxyCommand` / `connect.exe` 上花时间**——那是代理策略限制，不是参数问题。

### 13.4 推送后必须做的三步校验（缺一步就算没推完）

```powershell
# ① 确认无代理配置残留（三条都应无输出）
git config --local --get http.proxy; git config --global --get http.proxy; git config --local --get https.proxy

# ② 同步远端跟踪引用（推的是 URL 不是 remote 名，否则 git status 一直显示 ahead）
git -c http.proxy=http://172.16.0.11:3128 fetch https://github.com/lishengze/server_9.git master
git update-ref refs/remotes/origin/master FETCH_HEAD

# ③ 验证远端已收到：输出 SHA 应等于本地 git rev-parse HEAD
git -c http.proxy=http://172.16.0.11:3128 ls-remote https://github.com/lishengze/server_9.git refs/heads/master
```

收尾判据：`git status -sb` 显示 `## master...origin/master`（无 ahead），且 `git config --get http.proxy` 无输出。

### 13.5 规则（硬性）

1. **优先用 `git -c http.proxy=...` 一次性传参**，不写配置 → 天然不会残留代理。
2. 若必须写配置，**推送结束立即 `git config --unset http.proxy` / `--unset https.proxy`**，并在工作日志记一条"代理已取消"。
3. **推送后必须执行 §13.4 三步校验**，不能只看 `push` 的返回码——漏了 ② 会让下次会话误判"未推送"而重复提交。
4. 代理地址属环境信息，**换网络环境需向用户确认**，不假设固定值。
5. 推送失败先分辨是"网络不通"还是"权限/冲突"：`ssh ... Connection timed out` = 网络；`Could not read from remote repository` 且网络可达 = 权限/仓库名。

> 同类案例：其他项目（origin 亦为 SSH）在 `SHHQ-office` wifi 下同样直连超时，改用 HTTPS URL + 代理后 fetch/merge/push 全部成功。
