
# task_rule.md — Agent 通用工作规则（跨会话 / 跨项目 / 跨场景）

> 本文件是 Agent 执行任何任务的**统一行为规范**，由两部分融合而成：
> ① `task/task_all.txt` 第 1~15 行的工作准则（用户明确要求，长期遵守）；
> ② `task/task_upgrade.md` 的自我进化体系（工作/学习/总结/知识库方法论）。
>
> 适用范围：不同的会话、项目、场景、任务均可统一使用。
> **单一事实来源**：本文件是唯一权威源；`.chat/rules/project_rules.md`（面向所有 agent/会话的副本）由 `task/sync_rules.sh` 从本文件生成，**禁止手改副本**——先改本文件，再执行 `bash task/sync_rules.sh` 同步。

---

## 0. 总则

1. **一次任务，三份产出**：① 任务交付物；② 工作日志条目；③ 提炼后的知识条目。缺一不可。
2. **先把事做对，再求快**：改动前先理解，执行后必验证，产出必复查。
3. **验证优先，不凭猜测**：所有结论要有依据（编译通过/测试通过/日志证据/实测复现）。
4. **持续进化**：每次任务都是一次学习机会，把经验沉淀为可复用知识。

## 1. 工作流程规则（任务五阶段）

每个任务按五阶段执行：

### 阶段1 接单分类

- 判断任务类型：**编码 / 项目问答 / 通用问答 / 模糊任务**。
- 编码类 → 先收集项目信息；通用问答 → 直接回答不调工具；模糊任务 → 先澄清。

### 阶段2 规划

- 复杂任务用 `add_tasks` 拆解成可追踪子任务（id + 状态）。
- **先检索记忆/知识库/历史排障**，看有无现成答案，避免重复劳动。
- 明确验收标准（"什么叫完成"）。

### 阶段3 执行验证

- 改动前先读相关文件，不凭空猜测；修改用精准编辑，创建用新文件。
- **必须验证**：能编译的编译、能测试的测试、能部署的部署；文档类检查引用与格式。
- 开发测试一律在 docker `otc` 容器内 + CMake 重新编译部署，防旧库干扰。

### 阶段4 复查（多轮）

- 对所有产出执行**多轮复查**（§3：一轮=全量+六维度全检+台账；任一处改动即重开；**末轮零修改**才收工；进度写台账 §11.3）。

### 阶段5 沉淀提交

- 写工作日志 → 提炼知识 → 更新 Prompt.md → **显式询问用户是否提交 git**（若选择是，设置合适 commit 内容并推送到远程仓库）→ 关闭 docker。

## 2. 工作日志规则（来源：task_all.txt 第 1~3 行）

1. **每完成一次工作，记录一次工作日志**，将工作的时间、内容、效果、经验教训**分块**记录到 `work_log/` 对应日期的 markdown 文件。
2. **不要删除**当前工作日志的内容——这些内容可能来自其他主机/其他会话，**只能追加，不能覆盖**。
3. 若文件夹没有该日期文件，则创建该文件夹和日期文件，文件名格式 **`YYYYMMDD.md`**（如 `work_log/20261009.md`）。
4. **日期确定规则**：工作日志日期必须取系统 `date` 命令的**实际日期**，不采用对话上下文/系统提示中的日期（可能过时）。跨过午夜后，新工作必须新建对应 `YYYYMMDD.md`，**不得继续追加到昨天的文件**。
5. 日志模板见 §11.1；标题须严格沿用（`## 任务` / `### 结论` / `### 经验教训`），否则 `task/review/review_prepare.sh` 聚合不到（见 §8.5）。

## 3. 产出复查规则（来源：task_all.txt 第 4 条 + 双轴 Code Review）

**适用范围（强制，无例外条款）**：代码文件、SQL 脚本、测试代码、文档、配置、shell 脚本等**一切产出**。不因"改动很小""只改一行""赶时间""用户没说"而豁免。

### 3.1 用户原话（最高优先，不得降级）

> 对于代码文件、SQL 脚本、测试代码、文档等所有产出，均须执行以下复查流程：
> - 每一轮都复查、审核该轮涉及的内容，检查是否符合要求，进行查漏补缺的修改。
> - 反复审查所有生成的内容并修改完善，直到当前轮次结束后整个轮次没有一处需要修改。
> - 只要当前轮次结束后发现修改完善了一个内容，就再开启一轮全面的审查工作。

### 3.2 "一轮"的硬性定义（防走过场）

一轮复查 = 对**本轮全部产出**按 §3.3 六维度**逐条全检**，并留下一条台账记录（模板见 §11.3）。四条缺一不可：

| 要件 | 要求 | 反例（视为未做复查） |
|------|------|---------------------|
| **全量范围** | 本轮所有产出文件/命令/文档 | 只查自己最后改的那几行 |
| **全维全检** | §3.3 六维度逐条过，不抽样 | "看着没问题"就收工 |
| **有验证** | 能编译则编译、能测则测、能跑则跑、文档核引用 | 只声称"应该没问题" |
| **有台账** | 轮次/范围/发现/修改/结论入 work_log 或交付说明 | 口头说"复查过了" |

### 3.3 每轮必查六维度（固定清单，逐条勾）

| # | 维度 | 查什么 | 判"不通过"的典型 |
|---|------|--------|-----------------|
| ① | **需求符合** | 需求/验收标准逐条落实，无漏项、无擅自改需求 | 少实现一个字段或分支 |
| ② | **正确与边界** | 逻辑正确；空/零/越界/并发/超时/失败/重连等异常路径 | 空指针未判、超时未处理 |
| ③ | **一致性** | 跨文件/跨层的命名、类型、口径、字段顺序、章节号、编号一致 | 改了结构体字段顺序但调用处没跟改；章节号错位 |
| ④ | **引用可达** | 所有路径、文件名、章节号、符号、命令**真实存在**（`rg` 全局核对，非凭记忆） | 引用已删除的文件或已不存在的 §号 |
| ⑤ | **规范与风格** | 仓库标准 > Fowler 坏味道基线（§3.6）；命名/注释/格式/分层 | Mysterious Name、Duplicated Code |
| ⑥ | **可验证性** | 编译通过 / 测试通过 / 脚本跑通 / 数据可核对 / 文档可定位到源码与命令 | 无任何证据支撑结论 |

### 3.4 零修改判定与重开规则（核心）

**一轮判定"零修改"，必须同时满足**：① §3.3 六维度**全部勾过**；② 无任何待改项（**不是**"没时间改/下轮再说"）；③ 台账与验证证据齐全。

- **任一处被修改 → 本轮作废，重开一轮"全量"复查**（不是只复查被改的那一处）。第 N+1 轮必须重新覆盖 §3.3 六维度，因为一处改动会影响一致性/引用/边界。
- **终止条件**：出现**一轮零改动**即收工（该轮须六维度全勾、无待改项）；轮次**不设上限**，但绝大多数任务应在 2~3 轮内收敛。
- **收敛保护**：同一产出连续 **3 轮**仍在改同一处（反复改来改去），说明方案有问题——**回到 §1 阶段2 重新规划/拆解**，而不是继续硬改。
- **记录义务**：交付时必须能回答"做了几轮、每轮查了什么、末轮是否零改动"。

### 3.5 双轴审查（与六维度并行，代码类产出必做，参考 lsz-skills-real-engineers）

对于代码类产出，按**两个轴**并行审查，防止一个轴掩盖另一个：

| 轴                     | 评审内容                                             | 典型失败                   |
| ---------------------- | ---------------------------------------------------- | -------------------------- |
| **Standards 轴** | 代码是否符合仓库编码标准 + Fowler 坏味道基线（见下） | 实现了正确功能但代码质量差 |
| **Spec 轴**      | 代码是否忠实实现了需求/规格                          | 代码写得很漂亮但功能不对   |

两轴并行，报告分开呈现，不合并排序。

### 3.6 Fowler 坏味道基线（12 种）

适用于代码复查的 Standards 轴基线（§3.5）：

| 坏味道                           | 特征                       | 修复               |
| -------------------------------- | -------------------------- | ------------------ |
| **Mysterious Name**        | 名字不揭示功能             | 重命名             |
| **Duplicated Code**        | 相同逻辑出现在多处         | 提取共享           |
| **Feature Envy**           | 方法更多使用其他对象的数据 | 移到它嫉妒的数据上 |
| **Data Clumps**            | 相同字段总一起出现         | 打包成类型         |
| **Primitive Obsession**    | 基本类型代替领域概念       | 给概念自己的类型   |
| **Repeated Switches**      | 相同 switch/if 级联重复    | 多态或共享映射     |
| **Shotgun Surgery**        | 一个变化需散落多处编辑     | 集中到一个模块     |
| **Divergent Change**       | 一个文件因无关原因被改     | 拆分               |
| **Speculative Generality** | 添加了规格不需要的抽象     | 删除               |
| **Message Chains**         | 长 a.b().c().d() 导航      | 在第一个对象上隐藏 |
| **Middle Man**             | 类主要做委托               | 直接调用真实目标   |
| **Refused Bequest**        | 子类忽略大部分继承内容     | 组合替代继承       |

> 规则：仓库已有标准 > 坏味道基线；坏味道是判断调用，非硬违规；跳过工具已检查的内容。

## 4. 知识沉淀规则（来源：task_all.txt 第 5 行 + 自进化体系）

1. 当前知识库目录：`study/knowledge_base_system`（系统级：架构/开发/编译/部署/测试/排障/消息/数据流转/复盘体系；原业务级 `study/knowledge_base` 已整体并入本库），对工程各环节进行了总结。若其他项目另建业务级知识库 `study/knowledge_base`（业务细节/出入参/新旧映射），两级维度互补、互相引用而非重复。

2. **每次工作完成后，对此次工作所学的经验、教训进行总结**，更新到对应的知识库文档中。
3. **更新 `Prompt.md` 的内容**，使后续学习能覆盖最新知识（跨会话知识迁移）。
4. 遵循**知识生命周期**：捕获 → 验证 → 提炼 → 索引 → 应用 → 保鲜。
5. **禁止把未经证实的猜测写进知识库**；宁精勿滥，只沉淀可复用、有区分度的内容。
6. 用户纠正你基于记忆的陈述时，**必须更新/删除错误记忆**。

### 4.1 文档写作规范（writing-for-agents 要点）

知识库/Prompt.md 都是"给 agent 看的文档"，遵循以下规范（要点即下述五条）：

- **Context Pointer**：指针措辞决定 agent 何时触及材料，要写清"材料是什么 + 触发分支"。
- **信息层次**：步骤内联、参考按需查阅、细枝末节放指针后（渐进披露）。分支是最干净的披露测试。
- **引导词（Leading Word）**：用已存在于预训练的紧凑概念（如 `tight`/`red`）锚定行为，省 token 且更准。
- **正向引导，少用否定**：禁止指令会把禁止行为拖入上下文。
- **单一事实来源**：每个含义只在一个权威位置；环境能查到的（`--help`/配置文件）不要复述。
- **每行检查相关性**：无 no-op（不改变默认行为的指令）；过时的删除。

## 5. 开发测试环境规则（来源：task_all.txt 第 6~7 行）

1. 每次进行功能开发测试，都在 **docker `otc` 容器环境**下进行。
2. 使用 **CMake 重新编译部署所有组件**，防止旧的生成库干扰。
3. 每次涉及在 docker 中的功能开发测试完成后，**记得关闭 docker**，减少机器消耗。

## 6. 问题解决准则（来源：用户 2026-10-10 明确要求）

1. **遇到尝试三次以上仍解决不了的问题**，**先完整学习知识库中已总结的内容**（`study/knowledge_base_system/`、`memory/`（含 `MEMORY.md` 索引）、`work_log/`、`study/<模块>.md` 深度专题），**再去拓展性地思考解决方案**，不能一直重复排查已知问题。

2. 问题**解决之后**，若属于**新出现的问题**（知识库中未记录），**记得补充到知识库**（对应主题文档 + 记忆索引 + Prompt.md）。
3. 此准则需跨会话长期遵守。

### 6.1 Bug 诊断六阶段（错误驱动学习的执行版本）

> 铁律：**先建反馈回路，再提假设，最后才改代码**。跳步会导致"改了很多处才碰对"。

| 阶段 | 动作 | 通过标准 |
|------|------|---------|
| ① 复现 | 构造最小可复现命令/用例（脚本、单测、mock） | bug 能稳定出现，且能一键重跑 |
| ② 观察 | 收集证据：日志、栈、抓包、数据、队列状态；**此阶段不改代码** | 现象可量化（次数/耗时/字段值） |
| ③ 假设 | 提出**可证伪**的单一根因假设 | 假设能预测"改哪里会让现象消失" |
| ④ 验证 | 最小实验（探针/临时日志/单点改动），一次只验一个变量 | 现象按预测变化，根因确认 |
| ⑤ 修复 | 只改根因处，不动无关代码；标注为何这样改 | 现象消失，且未引入新问题 |
| ⑥ 回归 | 跑原有用例 + 补一条覆盖该 bug 的用例 | 回归通过；"现象→根因→解法"写入知识库 |

## 7. 学习规则

1. **主动学习 + 被动学习结合**：任务驱动学新功能，计划驱动回顾不熟悉领域。
2. **三层学习机制**（参考 agent_upgrade.md）：
   - **任务即时学习**：执行陌生/报错/复杂任务时，实时检索知识、补齐能力缺口；
   - **短板靶向学习**：基于复盘统计高频出错/低效任务，定向补弱（优先级：高频踩坑 > 业务刚需 > 通用能力 > 拓展知识）；
   - **常态化新知学习**：定期学习新技术/框架/规范/工具，拓宽能力边界。
3. **标准化学习 SOP（6 步）**：问题定位 → 资料检索 → 知识消化 → 实操验证 → 技能固化 → 迭代复用。
4. **学习钩子**：每次任务问自己三个问题——这是什么？怎么用/怎么配？坑在哪？
5. **跨会话知识迁移**：知识通过 `Prompt.md` 被下一会话 Agent 重新加载，实现继承。
6. 新功能研究产出到 `study/<功能号>_<业务名>/`，模式沉淀进知识库。

## 8. 复盘体系（四级复盘 + 成果固化）

> 参考 agent_upgrade.md，将"单任务复盘"升级为**四级复盘体系**，是 Agent 自进化的核心环节。

### 8.1 四级复盘体系

| 级别                       | 频率               | 内容                                                  |
| -------------------------- | ------------------ | ----------------------------------------------------- |
| **单任务即时复盘**   | 每次任务后（必做） | 用"复盘核心五问"轻量复盘单次任务得失                  |
| **每日总结复盘**     | 每日               | 汇总当日任务，统计高频问题/新增技能/能力短板          |
| **每周迭代复盘**     | 每周               | 迭代 SOP 流程、优化 Skill、清理无效知识、补充缺失能力 |
| **每月能力升级复盘** | 每月               | 盘点能力体系，对比月初基线，评估成长，制定下月计划    |

### 8.2 复盘核心五问（单任务即时复盘必问）

1. 本次任务是否完全达标？存在哪些瑕疵？
2. 执行中哪些步骤高效、可固化复用？
3. 出现了哪些报错/卡点/低效问题？根因是什么？
4. 下次同类任务如何优化流程、规避问题？
5. 需要新增/优化哪些 Skill、知识库条目？

### 8.3 复盘成果五转化（固化规范）

| 复盘发现 | 转化去向                                                |
| -------- | ------------------------------------------------------- |
| 高效经验 | → 固化为**标准化 Skill/流程模板**                |
| 报错踩坑 | → 录入**问题解决方案知识库**（现象→根因→解法） |
| 流程瑕疵 | → 优化**通用工作 SOP**（task_rule.md）           |
| 能力短板 | → 列入**靶向学习清单**                           |
| 优质案例 | → 存入**标杆案例库**复用                         |

### 8.4 复盘后知识库融合核查（必做，用户 2026-10-13 明确要求）

**每次进行 daily / weekly / monthly 复盘后，必须核查"当日的经验教训总结是否已融合到知识库中"**，避免"只出报告、不反哺"：

1. **逐条核对**：复盘输入文件（`task/review/<周期>_<日期>_input.md`）中列出的每条"经验教训"，逐一确认是否已写入对应知识库主题文档（`study/knowledge_base_system/` 或 `memory/`）。
2. **补写缺失**：对尚未沉淀的经验教训，立即补写进知识库对应主题文档，并同步更新 `MEMORY.md` 索引速查 + `Prompt.md`（实现跨会话知识迁移）。
3. **闭环确认**：全部经验教训都已在知识库中找到落点后，复盘才算真正闭环；在复盘报告中记录核查结果。

> 触发分支：执行 daily/weekly/monthly 复盘时，在"写复盘报告"步骤前执行本核查。

### 8.5 复盘触发机制与自动化边界（cron 半自动）

**核心结论**：Agent 是被动响应式，**无法自行唤醒**做日/周/月复盘（当前环境无 headless agent CLI，cron 只能跑 shell 脚本、无法启动带工具的 agent 会话）。因此：

| 级别 | 自动化程度 | 机制 |
|------|-----------|------|
| **单任务即时复盘** | ✅ 全自动 | 内嵌于任务收尾（§12 自检清单），无需外部触发 |
| **每日/每周/每月复盘** | ⚠️ 半自动 | cron 自动备数据 + 用户一句话触发 agent 执行反思 |

**半自动流程**（脚本 `task/review/review_prepare.sh`，包说明见 `task/review/README.md`）：

**cron 示例**（`crontab -e`，路径按项目实际根目录替换）：

## 13. git 提交与远程推送规则（代理，2026-10-29 新增，同日实测校准）

### 13.1 提交前

1. **先问用户**是否提交 git（§12）；用户同意后，**工作日志与知识库改动一并提交**，防止"代码提交了、日志没提交"。
2. **检查待提交内容**：`git status --short` + `git diff --stat`，确认没有误提交临时脚本/大文件/敏感信息（含密码的脚本必须清理，见 §7 教训）。
3. **先拉后推**：`git fetch` 刷新远端 tracking → 有他人提交则 `git merge`（或 `git pull --rebase`）后再推，避免 non-fast-forward。
4. **注意工作区里别人的改动**：`git status` 里出现不是本轮产出的文件（并发会话/用户手改），**只 `git add` 自己产出的路径**，不 `git add -A`。

### 13.2 推送需要代理时的处理（**用后必须取消**）

远端是 **SSH 地址** `git@github.com:lishengze/server_9.git`。**推送顺序：先试直连 SSH，不通再走 HTTPS+代理。**
 - **直连 SSH 可用时（2026-11-05 Linux 主机实测）**：`ssh -T git@github.com` 返回 `Hi lishengze!` → 直接 `git push origin master` 即可，**无代理、无残留**（实测一次推送成功）。
 - **直连不通时（2026-10-29 Windows 主机）**：直连 22/443 均超时，必须挂 HTTP 代理 **`172.16.0.11:3128`**（见下方脚本/命令）。

**推荐：直接用现成脚本**（内置探活重试 + 推后三步校验）：

```powershell
pwsh -NoProfile -File task/tool/git_push_proxy.ps1
# 可选参数：-Branch dev -RepoUrl <https-url> -Proxy 172.16.0.11:3128 -MaxMinutes 15
```

**手动等价命令**：

```powershell
cd D:\code\work\api_trunk
$env:GIT_TERMINAL_PROMPT='0'; $env:GCM_INTERACTIVE='never'   # 防交互卡死
git -c http.proxy=http://172.16.0.11:3128 push https://github.com/lishengze/server_9.git master
```

**关键：推的是 HTTPS URL，不是 `origin`** —— `origin` 是 SSH 地址，SSH 过不了代理（见 §13.3）。

**代理路径的 Linux 等价命令（备用，2026-11-05 实测代理探活 200）** —— 无需 PowerShell：

```bash
cd /home/lsz/code/work/api_trunk
export GIT_TERMINAL_PROMPT=0
curl -sS -m 8 -x http://172.16.0.11:3128 -o /dev/null -w '%{http_code}\n' https://github.com/   # 探活需 200
git -c http.proxy=http://172.16.0.11:3128 push  https://github.com/lishengze/server_9.git master
git -c http.proxy=http://172.16.0.11:3128 fetch https://github.com/lishengze/server_9.git master
git update-ref refs/remotes/origin/master FETCH_HEAD
```

### 13.3 环境实测结论（2026-10-29 Windows 主机实测；2026-11-05 Linux 主机复核）

| 路径 | 结果 | 说明 |
|------|------|------|
| 直连 `github.com:22` / `:443` | ❌ 超时 | `Test-NetConnection` 全 False |
| HTTPS 经代理 | ✅ 200，但**会成片 502** | 实测出现过连续 ~7 分钟、20 次探活全部 502，之后恢复；**必须用重试循环，不能试 2~3 次就放弃** |
| SSH 经代理（`connect.exe -H`/`-T`） | ❌ 隧道 200 但无 banner | 隧道能建立、随后 `Connection timed out during banner exchange` → **代理只放行 HTTPS，不放行 SSH** |
| HTTPS 凭据 | ✅ 无需交互 | Windows 凭据管理器已存 `git:https://github.com`（用户 `lishengze`） |
| 进程环境变量 | ⚠️ 已存在 `HTTP_PROXY`/`HTTPS_PROXY` | 由启动 dsh 的父进程注入（User/Machine 级均为空、不落盘），非本规则所设；**校验以 `git config` 无 proxy 项为准** |
| **直连 SSH（Linux 主机，2026-11-05）** | ✅ **可用** | `ssh -T git@github.com` → `Hi lishengze!`；`git push origin master` 成功（`143d763..49ec5b7`）。**Linux 主机优先直连 SSH，不必绕代理** |

> 结论 1：**不要在 `GIT_SSH_COMMAND` / `ProxyCommand` / `connect.exe` 上花时间**——那是代理策略限制，不是参数问题。
> 结论 2：**502 是常态性抖动，不是配置错误**。判定标准是 `curl -x <proxy> https://github.com/` 返回 200；拿到 200 后立刻推，成功率最高。
> 结论 3（2026-11-05 Linux 主机复核）：代理地址**跨主机一致可用**（探活 200）；直连 HTTPS 大包会中断（8s 收 366KB 后超时）→ 仍必须走代理。Linux 侧只需 `git -c http.proxy=... <https-url>`，无 PowerShell/凭据管理器依赖。

### 13.4 推送后必须做的三步校验（缺一步就算没推完）

```powershell
# ① 确认无代理配置残留（应无输出）
git config --list --show-origin | Select-String -Pattern 'proxy'

# ② 同步远端跟踪引用（推的是 URL 不是 remote 名，否则 git status 一直显示 ahead）
git -c http.proxy=http://172.16.0.11:3128 fetch https://github.com/lishengze/server_9.git master
git update-ref refs/remotes/origin/master FETCH_HEAD

# ③ 验证远端已收到：输出 SHA 应等于本地 git rev-parse HEAD
git -c http.proxy=http://172.16.0.11:3128 ls-remote https://github.com/lishengze/server_9.git refs/heads/master
```

收尾判据：`git status -sb` 显示 `## master...origin/master`（无 ahead），`git config` 无 proxy 项，`git remote -v` 仍是原 SSH 地址。

> `task/tool/git_push_proxy.ps1` 已把推送 + ②③ + 残留校验全部内置，一条命令完成。

### 13.5 规则（硬性）

1. **先试直连 SSH**（`ssh -T git@github.com`）；通了就 `git push origin master`，不用代理。需要代理时才用 `git -c http.proxy=...` 一次性传参（或跑 `task/tool/git_push_proxy.ps1`），不写配置 → 天然不会残留代理。
2. 若必须写配置，**推送结束立即 `git config --unset http.proxy` / `--unset https.proxy`**，并在工作日志记一条"代理已取消"。
3. **推送后必须执行 §13.4 三步校验**，不能只看 `push` 的返回码——漏了 ② 会让下次会话误判"未推送"而重复提交。
4. **502 用重试循环处理**（探活 200 → 立即推；最长等 10~15 分钟），不要因一次 502 就判定"网络不可用"而放弃推送。
5. 代理地址属环境信息，**换网络环境需向用户确认**，不假设固定值。
6. 推送失败先分辨是"网络不通"还是"权限/冲突"：`ssh ... Connection timed out` = 网络；`CONNECT tunnel failed, response 502` = 代理出口抖动（重试）；`Could not read from remote repository` 且网络可达 = 权限/仓库名。

> 同类案例：其他项目（origin 亦为 SSH）在 `SHHQ-office` wifi 下同样直连超时，改用 HTTPS URL + 代理后 fetch/merge/push 全部成功。
