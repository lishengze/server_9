# 三对象性能对比测试报告（GOne / GW 单链接单客户 / GW 单链接多客户）

## 测试配置
- **目标 TPS**：5000，持续 10 秒（预热 3 秒）
- **CPU 绑定**：统一绑定 **CPU 7**（系统 16 核中最空闲核，确保公平测量）
- **编译**：Release 模式
- **测试环境**：docker 容器 otc（host 网络模式），FTE(33001) + gone_counter_mock(44001/44002) + counter98_mock(9003)
- **日期**：2026-09-23
- **环境负载**：系统空闲（模拟交易所 tgw_simulator 已停止，避免其占 9 核导致时延失真）

> ⚠️ **重要说明**：模拟交易所 tgw_simulator 正常运行时占用约 9 核 CPU（持续撮合），会导致系统过载（load 13+），**使 FTE 场景 P90/P95 尾部延迟放大 10~40 倍**（P90 从 ~700ns 恶化到 ~8000ns）。本报告数据均在**系统空闲**状态下测得。详见文末"时延失真根因"。

## 分析场景
1. **API 内部打点延迟**：进入 API（`api_arrive_time_ns`）→ `send()` 系统调用成功前（`api_leave_time_ns`），即 API 层处理时延（不含网络发送）
2. **网卡抓包延迟**：进入 API（`api_arrive_time_ns`）→ 被网卡实际发送出去（AF_PACKET 抓包时间戳），即 API 处理 + 网络栈发送全链路时延

## 对比分析（系统空闲状态）

### 1. API 内部延迟（P50）
- **GOne 最优**：P50=321ns
- **GW 多客户**（P50=341ns）≈ **GW 单客户**（P50=371ns），差异不大
- 三者差距小（321~371ns），均处于极低延迟水平

### 2. API 内部延迟（P90）
- **GOne 最优**：P90=391ns
- **GW 多客户**（P90=561ns）优于 **GW 单客户**（P90=752ns）
- GOne 无 FTE 单线程 asio 瓶颈，P90 最平滑

### 3. 网卡全链路延迟（P50/P90）
- **GOne 最优**：P50=2124ns, P90=2525ns
- **GW 多客户**（P50=2274ns, P90=3029ns）优于 **GW 单客户**（P50=2745ns, P90=5479ns）
- 网卡发送固定开销（协议栈+系统调用）在 P50 上占主导，三对象差异缩小

### 4. 单客户 vs 多客户（系统空闲时的新发现）
- **多客户反而略优**（P50 341 vs 371，P90 561 vs 752）
- 高负载时单客户更优（P90 8355 vs 8626），但系统空闲时多客户更优
- 差异均不大（P50 差 ~30ns），说明 `single_cust_per_link` 优化在系统空闲时收益不明显，多客户 session 分摊反而略快

### 5. 整体结论
- **API 内部延迟**：GOne < GW多客户 < GW单客户（P50/P90 均成立）
- **网卡全链路延迟**：GOne < GW多客户 < GW单客户
- **GOne 优势**：协议消息短（64B vs 118B）、无 FTE 单线程 asio 瓶颈，P50/P90 均最优
- 三对象在系统空闲时均达到极低延迟（P50 < 400ns，P90 < 800ns）

## 时延失真根因（重要环境注意事项）

**现象**：同 API 代码，首次测试时 GW 场景 P90=8355~8626ns、P95=47504~59101ns，比历史数据（P90~800ns）高 10~40 倍。

**根因**：**模拟交易所 tgw_simulator 正常运行时占用约 9 核 CPU**（3 个进程各 ~300%），加上 FTE 3 核，系统 16 核基本满载（load 13+，idle<30%）。导致：
1. FTE 单线程 asio 处理变慢（委托处理排队）
2. 内核调度延迟暴增
3. mock_client 绑定的 CPU7 可能被未绑核的 tgw 抢占

**验证**：停止 tgw_simulator 后系统空闲（idle 71%），GW 场景 P90 从 16153ns 降到 752ns、P95 从 84105ns 降到 2900ns，完全恢复正常。

**建议**：进行 FTE 性能测试时，应确保系统空闲（停止 tgw_simulator 或将其绑核隔离），否则尾部延迟失真。
