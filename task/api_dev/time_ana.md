## 一、背景

性能测试通过 `perf_runner` 测量每笔委托在 API 内部的处理耗时：

```
lat = req.api_leave_time_ns - req.api_arrive_time_ns
```

其中 `api_arrive_time_ns` 在 `order_insert` 入口记录（请求到达 API），`api_leave_time_ns` 由引擎线程在 `send()` 前后记录（请求离开 API）。

### 1.1 历史演进

| 阶段 | 记录点 | 测量内容 | 典型值（GOne 10000TPS） | 问题 |
|:---|:---|:---|:---|:---|
| 原始算法（§5.1 前） | `deal_order_req` 返回后（入队后） | 组包 + 入队耗时 | 平均 434ns | 低估真实延迟，消息尚未发送 |
| 优化后（当前，§5.2） | `send_msg()` **后**（引擎线程） | 组包 + 入队 + 引擎消费 + send() 系统调用 + 可能的内核缓冲忙等 | 平均 2189ns | 包含系统调用/忙等，非纯框架延迟 |
| **本分析建议** | `send_msg()` **前**（引擎线程） | 组包 + 入队 + 引擎消费 | 待测 | 纯框架延迟，排除系统调用/内核干扰 |

## 二、记录点分析：send() 前 vs send() 后

### 2.1 `send_msg_fc` 的实现特性

```cpp
// tcp_ch.cpp:40-59
int32 tcp_ch::send_msg_fc(char *pmsg, int32 len) {
  ...
  while (is_work()) {
    ret = send(sysfd, pmsg + wlen, len - wlen, 0);  // flags=0（阻塞），MSG_DONTWAIT 被注释
    if (ret == len - wlen) return len;               // 全部发送成功
    else if (ret >= 0) { wlen += ret; continue; }    // 部分发送，继续
    else {
      if (errno == EAGAIN || EWOULDBLOCK || EINTR) {
        CPU_PAUSE(); continue;  // 内核缓冲满时忙等重试
      } else
        return LBERR_OBJ_WRITE_FAIL;
    }
  }
}
```

关键点：
- `send()` 用 `flags=0`（阻塞模式），`MSG_DONTWAIT` 被注释
- 发生 `EAGAIN`（内核发送缓冲区满）时 `CPU_PAUSE()` **忙等重试**
- 因此 `send_msg_fc` 是**阻塞式发送**，可能因内核缓冲满而忙等

### 2.2 两种记录点的测量含义

| 记录点 | 测量内容 | 包含的延迟成分 |
|:---|:---|---:|
| **send() 前** | 组包 + 入队 + 引擎消费 + 取消息 | ✅ 纯 API 框架处理延迟 |
| **send() 后** | 上述 + send() 系统调用 + 可能的内核缓冲忙等 | ❌ 含内核层/网络层开销 |

### 2.3 send() 后记录会引入的非框架开销

| 开销 | 来源 | 量级 | 是否属于 API 框架 |
|:---|:---|---:|:---:|
| 系统调用 | 用户态→内核态切换 | ~200-500ns | ❌ 内核层 |
| 数据拷贝 | 用户内存→内核 skb | ~100-300ns | ❌ 内核层 |
| 内核缓冲忙等 | EAGAIN → CPU_PAUSE() 自旋 | 不定（高 TPS 下显著） | ❌ 网络层/对端拥塞 |

### 2.4 结论：send() 前记录更合理

对于**框架性能基准**（对比优化前后、对比不同柜台）的测量目标，**send() 前记录更合理**：

1. **职责边界清晰**：API 框架的工作到 `send()` 调用为止，`send()` 是内核接口
2. **排除系统调用污染**：系统调用开销波动大（高 TPS 下上下文切换/缓存污染），会污染框架延迟测量
3. **排除内核缓冲忙等**：`send_msg_fc` 是阻塞式，EAGAIN 时忙等，后记录会因网络拥塞虚高框架延迟
4. **测量可重复性**：纯框架延迟应是稳定基准，不应受系统瞬时状态影响

> **注意**：如果测量目标是"端到端发送延迟"（数据进入内核缓冲），send() 后记录有意义。但严格说 send() 返回≠数据已到网卡/对端，真正的端到端延迟需对端确认或网卡硬件时间戳。

## 三、改动方案

### 3.1 改动内容

将引擎线程的 `api_leave_time_ns` 写入点从 `send_msg()` **后**移到 **前**：

```
改动前（当前）：
  ret = link_.send_msg(...);
  if (evt->leave_time_ptr) {
    __atomic_store_n(evt->leave_time_ptr, perf_now_ns(), __ATOMIC_RELEASE);
  }

改动后：
  if (evt->leave_time_ptr) {                          ← 移到 send 前
    __atomic_store_n(evt->leave_time_ptr, perf_now_ns(), __ATOMIC_RELEASE);
  }
  ret = link_.send_msg(...);
```

### 3.2 改动文件

| 文件 | 行号 | 分支数 |
|:---|:---:|:---:|
| `single_socket_engine.cpp` | 155-166 | 1 个 SEND_MSG 分支 |
| `multi_socket_engine.cpp` | 261-291 | 3 个发送分支（GW/Core/98） |
| `tcpdirect_engine.cpp` | 124-133 | 1 个 SEND_MSG 分支 |

### 3.3 改动说明

- **保持"成功/失败均写入"**：写入在 send() 前无条件执行，即使 send() 失败，时间戳也已写入，上层自旋会退出
- **注释更新**：将注释从 "send() 系统调用后" 改为 "send() 系统调用前"
- **不影响非委托事件**：非委托事件 `leave_time_ptr = nullptr`，判空跳过，不受影响

3. **FTE 最大延迟更差**（2713μs vs 1288μs），说明 gw counter 在高负载下存在更大的尾部延迟抖动

### 4.6 结论

- **send() 前记录更合理**：排除系统调用/内核缓冲忙等，测量结果更能反映 API 框架真实处理能力，且测试结果更稳定、可重复
- **推荐采用 send() 前记录**作为框架性能基准口径
- 若需测量端到端发送延迟，应另行使用网卡硬件时间戳或对端确认，而非 send() 前后

## 六、性能瓶颈全面分析与解决方案

### 6.1 FTE（gw counter）瓶颈分析

| 瓶颈 | 严重程度 | 根因 | 影响 |
|:---|:---:|:---|:---|
| **尾部延迟大（P95 2850ns）** | 🔴 致命 | ① `send_msg_fc` 阻塞式忙等（EAGAIN→CPU_PAUSE）<br>② 内核 TCP 栈抖动（系统调用/中断/锁）<br>③ FTE 模拟柜台处理波动 | P95 是 GOne 的 9.4 倍，平均被拉高 5.2x |
| **平均延迟高（2172ns）** | 🟠 严重 | 尾部延迟拉高平均（P50 仅 418ns） | 平均不反映真实性能 |
| **`send()` 系统调用开销** | 🟠 严重 | 每个委托一次 send()（flags=0，阻塞模式），MSG_DONTWAIT 被注释 | 占框架延迟的 82~94% |
| **跨进程通信** | 🟡 中等 | API → FTE → API 全链路，含内核网络栈 | 增加尾部抖动 |
| **单线程引擎** | 🟡 中等 | 单个引擎线程处理所有链路事件 | 高 TPS 下成为瓶颈 |

### 6.2 FTE 解决方案

#### 方案一：非阻塞发送 + 写就绪通知（优先级最高）
- **改动**：`tcp_ch::send_msg_fc` 启用 `MSG_DONTWAIT`，EAGAIN 时注册 epoll 写事件，而非 `CPU_PAUSE()` 忙等
- **效果**：消除内核缓冲满时的忙等自旋，大幅降低尾部延迟（预计 P95 从 2850→800ns）
- **风险**：需处理部分发送（短写）的重试逻辑，改动约 30 行
- **预计收益**：P95 ↓70%，平均 ↓50%

#### 方案二：引擎线程绑定专用核心
- **改动**：启动引擎线程时 `pthread_setaffinity_np` 绑定到隔离核心（如 CPU 14）
- **效果**：消除系统调度抖动，降低尾部延迟
- **风险**：低
- **预计收益**：P95 ↓30%，最大延迟 ↓50%

#### 方案三：批量发送（sendmmsg）
- **改动**：合并多个待发送消息，用 `sendmmsg()` 一次系统调用发送多个
- **效果**：减少系统调用次数，提升 TPS
- **风险**：需等待合并窗口，可能增加单笔延迟
- **预计收益**：TPS ↑10~20%

#### 方案四：减少心跳频率
- **改动**：心跳频率从 1s 改为 3~5s（或心跳线程不绑定到引擎核心）
- **效果**：减少心跳消息对委托链路的干扰
- **风险**：低
- **预计收益**：尾部延迟 ↓10%

#### 方案五：用户态协议栈（DPKM/io_uring）
- **改动**：使用 DPDK 或 io_uring 替代阻塞 TCP send
- **效果**：完全绕过内核网络栈，消除系统调用开销
- **风险**：改动大（需重写网络层），运维复杂
- **预计收益**：延迟接近 GOne（200~400ns）
- **建议**：远期规划，短期不建议

### 6.3 GOne（fpga_direct）瓶颈分析

| 瓶颈 | 严重程度 | 根因 | 影响 |
|:---|:---:|:---|:---|
| **平均被尾部拉高（747ns vs P50 245ns）** | 🟡 中等 | 少量长尾（最大 2987μs）拉高平均 | 平均不反映真实性能 |
| **序列化开销** | 🟢 轻微 | `pad_copy` + `checksum_bytes` 双趟序列化 | 约 50~100ns |
| **系统调用** | 🟢 轻微 | `send()` 系统调用（虽非阻塞） | 约 200~300ns |

### 6.4 GOne 优化建议

| 优化项 | 预计收益 | 改动量 | 优先级 |
|:---|:---:|:---:|:---:|
| 引擎线程绑定专用核心 | P95 ↓20%，最大 ↓50% | 低（几行代码） | 高 |
| 减少心跳频率 | 尾部延迟 ↓10% | 低 | 中 |
| 批量发送（sendmmsg） | TPS ↑5~10% | 中 | 低（TPS 已接近上限） |

### 6.5 综合建议

1. **短期（1-2 天）**：FTE 启用非阻塞发送（方案一）+ 引擎线程绑核（方案二），预计 P95 从 2850→800ns
2. **中期（1 周）**：实现批量发送（方案三），提升 TPS 至 10000+
3. **长期**：评估用户态协议栈（方案五），缩小与 GOne 的差距
