## 一、背景

性能测试通过 `perf_runner` 测量每笔委托在 API 内部的处理耗时：

```
lat = req.api_leave_time_ns - req.api_arrive_time_ns
```

其中 `api_arrive_time_ns` 在 `order_insert` 入口记录（请求到达 API），`api_leave_time_ns` 由引擎线程在 `send()` 前后记录（请求离开 API）。

### 1.1 历史演进

| 阶段 | 记录点 | 测量内容 | 典型值（GOne 10000TPS） | 问题 |
|:---|:---|:---|:---|:---|
| 原始算法（§5.1 前） | `deal_order_req` 返回后（入队后） | 组包 + 入队耗时 | 平均 434ns | 低估真实延迟，消息尚未发送 |
| 优化后（当前，§5.2） | `send_msg()` **后**（引擎线程） | 组包 + 入队 + 引擎消费 + send() 系统调用 + 可能的内核缓冲忙等 | 平均 2189ns | 包含系统调用/忙等，非纯框架延迟 |
| **本分析建议** | `send_msg()` **前**（引擎线程） | 组包 + 入队 + 引擎消费 | 待测 | 纯框架延迟，排除系统调用/内核干扰 |

## 二、记录点分析：send() 前 vs send() 后

### 2.1 `send_msg_fc` 的实现特性

```cpp
// tcp_ch.cpp:40-59
int32 tcp_ch::send_msg_fc(char *pmsg, int32 len) {
  ...
  while (is_work()) {
    ret = send(sysfd, pmsg + wlen, len - wlen, 0);  // flags=0（阻塞），MSG_DONTWAIT 被注释
    if (ret == len - wlen) return len;               // 全部发送成功
    else if (ret >= 0) { wlen += ret; continue; }    // 部分发送，继续
    else {
      if (errno == EAGAIN || EWOULDBLOCK || EINTR) {
        CPU_PAUSE(); continue;  // 内核缓冲满时忙等重试
      } else
        return LBERR_OBJ_WRITE_FAIL;
    }
  }
}
```

关键点：
- `send()` 用 `flags=0`（阻塞模式），`MSG_DONTWAIT` 被注释
- 发生 `EAGAIN`（内核发送缓冲区满）时 `CPU_PAUSE()` **忙等重试**
- 因此 `send_msg_fc` 是**阻塞式发送**，可能因内核缓冲满而忙等

### 2.2 两种记录点的测量含义

| 记录点 | 测量内容 | 包含的延迟成分 |
|:---|:---|---:|
| **send() 前** | 组包 + 入队 + 引擎消费 + 取消息 | ✅ 纯 API 框架处理延迟 |
| **send() 后** | 上述 + send() 系统调用 + 可能的内核缓冲忙等 | ❌ 含内核层/网络层开销 |

### 2.3 send() 后记录会引入的非框架开销

| 开销 | 来源 | 量级 | 是否属于 API 框架 |
|:---|:---|---:|:---:|
| 系统调用 | 用户态→内核态切换 | ~200-500ns | ❌ 内核层 |
| 数据拷贝 | 用户内存→内核 skb | ~100-300ns | ❌ 内核层 |
| 内核缓冲忙等 | EAGAIN → CPU_PAUSE() 自旋 | 不定（高 TPS 下显著） | ❌ 网络层/对端拥塞 |

### 2.4 结论：send() 前记录更合理

对于**框架性能基准**（对比优化前后、对比不同柜台）的测量目标，**send() 前记录更合理**：

1. **职责边界清晰**：API 框架的工作到 `send()` 调用为止，`send()` 是内核接口
2. **排除系统调用污染**：系统调用开销波动大（高 TPS 下上下文切换/缓存污染），会污染框架延迟测量
3. **排除内核缓冲忙等**：`send_msg_fc` 是阻塞式，EAGAIN 时忙等，后记录会因网络拥塞虚高框架延迟
4. **测量可重复性**：纯框架延迟应是稳定基准，不应受系统瞬时状态影响

> **注意**：如果测量目标是"端到端发送延迟"（数据进入内核缓冲），send() 后记录有意义。但严格说 send() 返回≠数据已到网卡/对端，真正的端到端延迟需对端确认或网卡硬件时间戳。

## 三、改动方案

### 3.1 改动内容

将引擎线程的 `api_leave_time_ns` 写入点从 `send_msg()` **后**移到 **前**：

```
改动前（当前）：
  ret = link_.send_msg(...);
  if (evt->leave_time_ptr) {
    __atomic_store_n(evt->leave_time_ptr, perf_now_ns(), __ATOMIC_RELEASE);
  }

改动后：
  if (evt->leave_time_ptr) {                          ← 移到 send 前
    __atomic_store_n(evt->leave_time_ptr, perf_now_ns(), __ATOMIC_RELEASE);
  }
  ret = link_.send_msg(...);
```

### 3.2 改动文件

| 文件 | 行号 | 分支数 |
|:---|:---:|:---:|
| `single_socket_engine.cpp` | 155-166 | 1 个 SEND_MSG 分支 |
| `multi_socket_engine.cpp` | 261-291 | 3 个发送分支（GW/Core/98） |
| `tcpdirect_engine.cpp` | 124-133 | 1 个 SEND_MSG 分支 |

### 3.3 改动说明

- **保持"成功/失败均写入"**：写入在 send() 前无条件执行，即使 send() 失败，时间戳也已写入，上层自旋会退出
- **注释更新**：将注释从 "send() 系统调用后" 改为 "send() 系统调用前"
- **不影响非委托事件**：非委托事件 `leave_time_ptr = nullptr`，判空跳过，不受影响

3. **FTE 最大延迟更差**（2713μs vs 1288μs），说明 gw counter 在高负载下存在更大的尾部延迟抖动

- **send() 前记录更合理**：排除系统调用/内核缓冲忙等，测量结果更能反映 API 框架真实处理能力，且测试结果更稳定、可重复
- **推荐采用 send() 前记录**作为框架性能基准口径
- 若需测量端到端发送延迟，应另行使用网卡硬件时间戳或对端确认，而非 send() 前后

### 5.5 P95 分析——FTE 尾部延迟的关键瓶颈

**最显著的发现是 P95 的差距**：FTE 的 P95(2850ns) 是 GOne 的 P95(304ns) 的 **9.4 倍**，且 FTE 的 P95 远高于自身 P90(599ns)，说明：

| 指标 | FTE | GOne | 含义 |
|:---|---:|---:|:---|
| P50→P90 跨度 | 418→599（+181ns） | 245→277（+32ns） | FTE 中间段分布更宽 |
| P90→P95 跨度 | 599→**2850**（+2251ns） | 277→**304**（+27ns） | **FTE 有 5% 请求尾部剧增** |
| 平均 vs P50 | 2172 vs 418（5.2x） | 747 vs 245（3.0x） | FTE 平均被长尾严重拉高 |

**FTE 尾部延迟的根因（初步）**：
1. **`send_msg_fc` 阻塞式发送**：EAGAIN 时 `CPU_PAUSE()` 忙等，内核缓冲满时延迟剧增
2. **内核 TCP 栈抖动**：系统调用、中断、软中断处理、锁竞争导致偶发延迟尖峰
3. **FTE 模拟柜台处理波动**：FTE 侧（容器内）处理回报时偶发调度延迟
4. **跨进程通信**：mock_client → API → FTE → API → mock_client 全链路，任何一环波动都放大尾部

### 5.6 深入根因分析——P90/P95 突然增大的机制（代码级证据，2026-09-17）

**核心问题**：为什么 FTE 的 P50(401ns) 很低、P90(2755ns)/P95(9277ns) 突然剧增，而 GOne 全程平坦（311→452ns）？

**关键认知**：send-before 测量口径 `lat = api_leave_time_ns - api_arrive_time_ns` 是"入队 + 引擎线程处理到该消息（send 前）"的时间。**虽然不含 send() 本身，但包含引擎线程被前序消息 send() 忙等阻塞导致的排队时间**。这是理解尾部延迟的钥匙。

#### 5.6.1 全链路单线程串行架构（代码证据）

| # | 环节 | 代码证据 | 含义 |
|:---:|:---|:---|:---|
| 1 | API 引擎单线程忙轮询 | `single_socket_engine` 继承 `simple_thread`，`need_work()` 恒 true；`cmt_req_que_mem` 中 `trigger_send()` 被注释 | 发送（do_work）+ 接收（deal_recv）+ 心跳全在一个线程，无并行 |
| 2 | **`send_msg_fc` 阻塞忙等** | `common/src/tcp_ch.cpp:40-59`：`send(fd, buf, len, 0)` flags=0 阻塞模式，`MSG_DONTWAIT` 被注释；EAGAIN/EWOULDBLOCK 时 `CPU_PAUSE()` 忙等重试 | **内核缓冲满时引擎线程被钉死自旋**，不释放 CPU 也不让出线程 |
| 3 | **FTE 单线程 boost::asio** | `fte/src/main.cpp:512`：`ios_thread = std::thread([](){ GET_GLOBAL_TCP_ENGINE()->io_service_.run(); })` | **所有 TCP 连接（客户端 API + 模拟交易所 TGW）的接收/处理/发送在同一个 asio 线程串行执行** |
| 4 | FTE 委托处理完全同步 | `ccu_trade_impl::on_message` → `DealTradeOrderReq` → `DealTradeOrderReqBusi` → `SendOrderToExch` → `sz_binary::DealOrder`（编码+校验和+路由+asio 写 TGW） | FTE 处理委托的 CPU 工作（非网络写）是同步串行 |
| 5 | FTE 回报同步回传 | TGW 回报 → `DealReport` → `SendReportTradeOrderER` → `SendTradeOrderER`（同一 asio 线程直接写客户端） | 回报处理与委托处理互相挤占同一线程 |

#### 5.6.2 背压传导机制（P90/P95 剧增的完整链条）

```
客户端 10000 TPS 匀速发单
  ↓
FTE 单线程 asio 处理能力约 8500~9400 TPS（委托转发 TGW + 回报回传全在一个线程）
  ↓ 处理跟不上 → FTE 侧 TCP 接收缓冲积压
  ↓ → TCP 接收窗口收缩（甚至 0 窗口）→ 对端通告窗口变小
  ↓ → 客户端内核发送缓冲满 → send() 返回 EAGAIN
  ↓ → send_msg_fc 进入 CPU_PAUSE() 忙等 ← 引擎线程被阻塞（微秒~百微秒级）
  ↓ → 期间 send_queue_ 积压 N 条消息
  ↓ → 忙等结束，引擎线程恢复，积压消息被批量处理
  ↓ → 每条积压消息的排队时间 ≈ 忙等时长，被计入延迟
  ↓
结果：一次 EAGAIN 事件 → 一批消息延迟集体升高 → P90/P95 拖尾
```

**为什么 P50 依然很低**：稳态下引擎线程空闲、队列空，消息入队立即处理，延迟=纯处理时间（~400ns），与 GOne 差距不大（1.3x）。

**为什么 P90(2755) 与 P95(9277) 跨度大**：
- **P90 附近**：短时背压（EAGAIN 忙等几十微秒），对应 FTE 偶发处理停顿
- **P95 附近**：长时背压（百微秒~毫秒），对应 FTE 侧一次较长的停顿（对象池分配/日志/timer/容器调度抢占），或 TCP 窗口恢复的慢启动
- **最大 9294μs**：极端情况（FTE 毫秒级停顿，如日志 flush、调度器被抢占）

#### 5.6.3 实测佐证

1. **绑核后 P90 2755→599ns（↓78%）**：证明 CPU 调度抖动是 P90 拖尾的重要来源（引擎线程被调度器迁移/抢占）
2. **绑核后 P95 仍 2850ns**：证明 P95 尾部主要来自 TCP 背压/FTE 处理停顿（系统因素），非 CPU 调度
3. **TPS 缺口即背压证据**：FTE 实际 8503~9439 vs 请求 10000，**缺口 5~15% 恰好是 FTE 处理不过来的量化证据**——积压必然发生，背压必然传导

#### 5.6.4 GOne 为什么没有尾部延迟

- FPGA 硬件处理，无进程/无 TCP 栈/无 docker/无调度
- 处理能力远超 10000 TPS，永不背压，send() 永不 EAGAIN
- P50→P95 跨度仅 311→452ns（+141ns），分布平坦

### 5.7 瓶颈分析（绑定后）

1. **GOne 优势显著放大**：平均快 65.6%、P50/P75/P90 快 41~54%、**P95 快 89%**
2. **GOne 延迟极稳定**：P50→P95 仅 245→304ns（跨度 59ns），几乎无尾部延迟
3. **FTE 尾部延迟是最大瓶颈**：P95(2850ns) 远高于 P90(599ns)，5% 请求拖垮平均
4. **TPS**：GOne 9546 vs FTE 9156，GOne 高 4.3%

### 6.1 FTE（gw counter）瓶颈分析

### 6.2 FTE 解决方案

#### 方案一：非阻塞发送 + 写就绪通知（优先级最高）
- **改动**：`tcp_ch::send_msg_fc` 启用 `MSG_DONTWAIT`，EAGAIN 时注册 epoll 写事件，而非 `CPU_PAUSE()` 忙等
- **效果**：消除内核缓冲满时的忙等自旋，大幅降低尾部延迟（预计 P95 从 2850→800ns）
- **风险**：需处理部分发送（短写）的重试逻辑，改动约 30 行
- **预计收益**：P95 ↓70%，平均 ↓50%

#### 方案二：引擎线程绑定专用核心
- **改动**：启动引擎线程时 `pthread_setaffinity_np` 绑定到隔离核心（如 CPU 14）
- **效果**：消除系统调度抖动，降低尾部延迟
- **风险**：低
- **预计收益**：P95 ↓30%，最大延迟 ↓50%

#### 方案三：批量发送（sendmmsg）
- **改动**：合并多个待发送消息，用 `sendmmsg()` 一次系统调用发送多个
- **效果**：减少系统调用次数，提升 TPS
- **风险**：需等待合并窗口，可能增加单笔延迟
- **预计收益**：TPS ↑10~20%

#### 方案四：减少心跳频率
- **改动**：心跳频率从 1s 改为 3~5s（或心跳线程不绑定到引擎核心）
- **效果**：减少心跳消息对委托链路的干扰
- **风险**：低
- **预计收益**：尾部延迟 ↓10%

#### 方案五：用户态协议栈（DPKM/io_uring）
- **改动**：使用 DPDK 或 io_uring 替代阻塞 TCP send
- **效果**：完全绕过内核网络栈，消除系统调用开销
- **风险**：改动大（需重写网络层），运维复杂
- **预计收益**：延迟接近 GOne（200~400ns）
- **建议**：远期规划，短期不建议

#### 方案六：FTE 侧多线程 asio（消除背压源头，需协调对端）
- **改动**：`fte/src/main.cpp:512` 的 `io_service_.run()` 改为多线程（如 2~4 个 `ios_thread`），或按连接类型拆分 io_service（客户端连接与 TGW 连接分开）
- **效果**：提升 FTE 处理能力至 10000+ TPS，从源头消除 TCP 背压（P90/P95 剧增的根本原因）
- **风险**：FTE 是客户提供代码，需协调 FTE 团队；多线程共享对象需加锁（OrderManager/fund_data 等）
- **预计收益**：P95 ↓80%+（背压消失后尾部延迟主要剩内核抖动）
- **注意**：这是**治本**方案——§5.6 已证明背压源头是 FTE 单线程处理能力 < 发单速率

#### 方案七：客户端限流（过载测试认知修正）
- **认知**：10000 TPS 已超过 FTE 单线程处理能力（~8500-9400），属于**过载测试**，P90/P95 剧增是过载的必然结果，不是框架缺陷
- **改动**：压测时按对端实际能力限流（如 8000 TPS），或对端扩容后再测 10000
- **效果**：P90/P95 回到稳态水平（绑核后 P90=599ns 量级）
- **风险**：无
- **建议**：与方案六配合——对端能力不足时限流，对端扩容后测满负荷

## 七、gw counter 非阻塞发送 + 写就绪通知优化记录（2026-09-18）

> 本节对应 §6.2 方案一（优先级最高）的**落地实现与完整复盘**。核心改动不在 `tcp_ch` 层而在 `aio_tcp` 层（gw counter 实际发送路径），并经历了方案演进与 v2 无锁快速路径修复。

### 7.1 优化背景与目标

- **背景**：§5.5/§5.6 已证明 FTE（gw counter）的最大瓶颈是 P90/P95 尾部延迟（P95 为 GOne 的 9.4 倍）。§5.6 背压传导链指出，当发单速率超过 FTE 单线程 asio 处理能力（~8500 TPS）时，TCP 接收窗口收缩 → 客户端内核发送缓冲满 → `send_msg_fc` 进入 `CPU_PAUSE()` **忙等自旋** → 引擎线程被钉死 → 一批消息排队延迟集体升高。
- **目标**：消除内核缓冲满时的**忙等自旋**，让引擎线程在发送受阻时立即返回（不阻塞），把"等待可写"交给 epoll 写就绪事件异步处理，从而消除背压导致的批量尾部延迟。
- **对应方案**：§6.2 方案一（非阻塞发送 + 写就绪通知，预计 P95 ↓70%、平均 ↓50%）。

### 7.2 代码修改原理

#### 7.2.1 方案演进（为什么最终落在 aio_tcp 层）

| 方案 | 位置 | 做法 | 结果 |
|:---|:---|:---|:---|
| **原版** | `tcp_ch::send_msg_fc` | `send(fd, buf, len, 0)` 阻塞 + EAGAIN 时 `CPU_PAUSE()` 忙等 | 阻塞引擎线程，尾部延迟高 |
| **方案 A'** | `tcp_ch.cpp` | 用 `poll()` 等待可写再发送 | **实测更差（P95 26781ns），已回退** |
| **方案 B（最终）** | `aio_tcp.h` | `send_msg_fc` 改为 `MSG_DONTWAIT` 非阻塞 + EAGAIN 暂存 `pending_buf_` + 注册 EPOLLOUT | ✅ 采用 |

> **为什么方案 A' 更差**：`poll()` 等待可写仍让引擎线程**同步阻塞**在等待上，只是把 `CPU_PAUSE` 自旋换成了 poll 系统调用，且每次部分发送都要进内核 poll 一次，开销反而更大。**方案 B 的关键是"发送线程绝不等待"**——把等待交给独立的接收线程（epoll 事件驱动）去补发，引擎线程可继续处理下一条消息。

#### 7.2.2 核心改动 1：`aio_tcp.h::send_msg_fc` 重写为异步非阻塞

```cpp
int32 send_msg_fc(char *pmsg, int32 len) {
  // 无锁快速路径：无 pending 时直接非阻塞发送（最常见路径，避免 mutex 开销）
  if (!pending_active_.load(std::memory_order_acquire)) {
    int32 ret = ::send(ch.sys_fd(), pmsg, len, MSG_DONTWAIT);
    if (ret == len)
      return len;                                   // 完整发送成功，无锁返回
    std::lock_guard<std::mutex> lk(send_mtx_);      // 部分发送或 EAGAIN 才加锁
    if (ret >= 0) {
      if (ret < len) {                              // 短写：剩余部分暂存
        pending_buf_.assign(pmsg + ret, pmsg + len);
        pending_off_ = 0;
        pending_active_.store(true, std::memory_order_release);
        register_write_locked();                    // 注册 EPOLLOUT
      }
      return ret;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK || errno == EINTR) {
      pending_buf_.assign(pmsg, pmsg + len);        // 全部暂存
      pending_off_ = 0;
      pending_active_.store(true, std::memory_order_release);
      register_write_locked();
      return 0;
    }
    return LBERR_OBJ_WRITE_FAIL;
  }
  // 有 pending：加锁，先补发上一批 pending 再发送
  std::lock_guard<std::mutex> lk(send_mtx_);
  flush_pending_locked();
  if (!pending_buf_.empty())
    return 0;
  int32 ret = ::send(ch.sys_fd(), pmsg, len, MSG_DONTWAIT);
  // ... 与上面相同的部分发送/EAGAIN 处理
}
```

**原理**：
1. **`MSG_DONTWAIT` 非阻塞**：`send()` 立即返回，内核缓冲满时返回 `EAGAIN` 而非阻塞等待。
2. **EAGAIN/短写 → 暂存 `pending_buf_`**：把未发送的字节暂存到用户态缓冲，引擎线程**立即返回**（返回已发送字节数），不阻塞。
3. **注册 EPOLLOUT 写事件**：当 socket 可写时（内核缓冲腾出空间），由接收线程回调补发 `pending_buf_`。
4. **v2 无锁快速路径**：`pending_active_` 原子标志表示当前是否有 pending。**pending 为空时（绝大多数情况）直接 `::send()` 无锁**，只有部分发送/EAGAIN 才加锁。**避免 v1 无条件加锁导致的 P50 退化**（见 7.4.1）。

#### 7.2.3 核心改动 2：`wait_poll.cpp::mode_wake` 支持 EPOLLOUT

```cpp
int32 wait_poll_multi::mode_wake(epoll_event_op &pinfo) {
  struct epoll_event eventValue;
  eventValue.events = EPOLLIN | EPOLLERR;
  if (pinfo.isout == 1)
    eventValue.events |= EPOLLOUT;   // 需要写事件（非阻塞发送补发 pending）
  if (pinfo.isedge == 1)
    eventValue.events |= EPOLLET;
  eventValue.data.ptr = reinterpret_cast<void *>(&pinfo);
  if (epoll_ctl(epollfd, EPOLL_CTL_MOD, pinfo.get_fd(), &eventValue) < 0)
    return LBERR_OBJ_MOD_FAIL;
  return 0;
}
```

**原理**：复用 `mthread::mode_poll_event` 的 `isout` 标志，在 `EPOLLIN|EPOLLERR` 基础上按需加上 `EPOLLOUT`，实现写事件的**动态注册/取消**。EPOLLOUT 触发时接收线程调用 `flush_pending()` 补发 pending 缓冲。

#### 7.2.4 配套改动

| 改动 | 说明 |
|:---|:---|
| 新增成员 | `pending_buf_`（`std::vector<char>`）、`pending_off_`（`size_t`）、`write_registered_`（`bool`）、`send_mtx_`（`std::mutex`）、`pending_active_`（`std::atomic<bool>`） |
| 新增方法 | `flush_pending()`、`flush_pending_locked()`、`register_write_locked()`、`unregister_write_locked()` |
| `deal_event()` | **先 `flush_pending` 再 `loop_deal_recv`**：EPOLLOUT 触发时优先补发 pending，再处理接收 |
| `close_ch()` | 清理 pending 缓冲 + 取消 EPOLLOUT 注册 |

### 7.4 全面影响

#### 7.4.1 负面影响与修复

| 问题 | 现象 | 根因 | 修复 |
|:---|:---|:---|:---|
| **P50 退化（v1）** | P50 从 291→321ns | v1 对每次发送**无条件加 `send_mtx_` 锁**，正常发送路径引入 mutex 开销 | **v2 无锁快速路径**：`pending_active_` 原子标志，pending 空时直接 `::send()` 无锁，P50 恢复 ~300ns |

#### 7.4.2 代码级负面影响分析（详细）

> 基于 `aio_tcp.h` 与引擎调用处（`single_socket_engine.cpp:161` / `multi_socket_engine.cpp`）的代码审查，发现 **7 项负面影响**，其中 **2 项为严重级别的静默丢单缺陷**。

##### 7.4.2.1 🔴 严重：pending 期间后续消息静默丢弃（pending_buf_ 非队列缺陷）

**最严重的逻辑缺陷**。`pending_buf_` 是**单条消息缓冲，不是队列**。看 `send_msg_fc` 的关键路径：

```cpp
// line 181-185：有 pending 时
std::lock_guard<std::mutex> lk(send_mtx_);
flush_pending_locked();
if (!pending_buf_.empty())
  return 0; // ← 新消息被丢弃！未暂存、未发送
```

**触发场景**：
1. 消息 A 触发 EAGAIN → 暂存 `pending_buf_`
2. 引擎继续处理消息 B，调用 `send_msg_fc`
3. 进入"有 pending"分支，`flush_pending_locked()` 尝试补发 A 但**仍不可写**（`pending_buf_` 仍非空）
4. **`return 0`**——消息 B 被静默丢弃
5. 上层引擎只检查 `ret < 0`，`return 0` 被当作成功，**无任何错误日志或重试**

**实测 0 失败的解释**：单客户/单链接场景下引擎线程一次只处理一条消息（串行），且 FTE 能力内 EAGAIN 极少。但在**持续过载**（10000 TPS > FTE 8500 TPS）时 EAGAIN 频繁，此缺陷会真实触发——pending 补发期间到达的后续消息静默丢失。

##### 7.4.2.2 🔴 严重：flush 出错时 pending 静默丢弃

`flush_pending_locked()` 中非 EAGAIN 错误时：

```cpp
// line 232-237
// 出错：丢弃 pending，取消注册
pending_buf_.clear();
pending_off_ = 0;
pending_active_.store(false, std::memory_order_release);
unregister_write_locked();
return;
```

如果 `send()` 返回 `EPIPE`（对端已关闭连接）、`ECONNRESET` 或其他错误，pending 中的消息被直接清除。上层已认为这些消息"发送成功"（`send_msg_fc` 之前返回了 0/部分字节），**消息永久丢失，无任何告警**。

##### 7.4.2.3 🟠 中等：返回语义变化导致上层无法感知真实发送状态

| 返回值 | 原版语义 | 异步版语义 | 上层处理 |
|:---|:---|:---|:---|
| `len` | 全部发出 | 全部发出 | ✅ 正确 |
| `0` | 不可能（阻塞直到发完） | **EAGAIN 全部暂存 pending**，或 **pending 忙时丢弃新消息** | ❌ 当成功（`ret<0` 不触发） |
| `部分(<len)` | 不可能（阻塞直到发完） | 部分发出，剩余 pending | ❌ 当成功 |

上层引擎（`single_socket_engine.cpp:162`）只有 `if (unlikely(ret < 0))` 一个判断。**0 和部分字节都被当作成功**，无法区分"真正发出"和"暂存 pending"。

##### 7.4.2.4 🟡 中等：接收线程负载增加，可能延迟回报接收

```cpp
// line 569-572
virtual void deal_event() {
  flush_pending();      // ← 新增：先补发 pending
  loop_deal_recv();     // ← 后处理接收
}
```

接收线程（`mthread recv_th_`）现在既要处理回报接收，又要补发 pending。如果 pending 积压大（`flush_pending_locked` 的 while 循环多次重试），**回报接收被延迟**，可能导致回报到达后处理不及时（回调延迟增大），或对端心跳超时断链。

##### 7.4.2.5 🟡 中等：断链时 pending 未发出消息静默丢弃

```cpp
// line 550-563
void close_ch(int32 err = 0) {
  {
    std::lock_guard<std::mutex> lk(send_mtx_);
    pending_buf_.clear();     // ← 丢弃未发出的消息
    pending_off_ = 0;
    pending_active_.store(false, std::memory_order_release);
    // ... 取消 EPOLLOUT
  }
  ch.close_ch(err);
}
```

`close_ch` 时清理 pending。断链时所有暂存未发的消息被丢弃，而上层已认为它们"发送成功"。

##### 7.4.2.6 🟢 轻微：每次 EAGAIN 触发堆内存分配

```cpp
pending_buf_.assign(pmsg, pmsg + len);  // 堆分配
```

每次 EAGAIN 都触发 `std::vector::assign` 的堆内存分配（可能 realloc）。高 EAGAIN 场景下引入堆分配抖动（~50-200ns/次）、内存碎片，可能加剧延迟不稳定。

##### 7.4.2.7 🟢 轻微：心跳消息返回值被忽略，过载时可能丢失

```cpp
// single_socket_engine.cpp:173
link_.send_msg(heart_buf, heart_len);  // 返回值被忽略
```

心跳不走 `ret<0` 判断。如果心跳恰好在 pending 满时发送，可能被静默丢弃（`return 0`），多次心跳丢失可能导致对端超时断链。

##### 7.4.2.8 负面影响矩阵汇总

| # | 负面影响 | 严重程度 | 触发条件 | 发生概率 |
|:---:|:---|:---:|:---|:---:|
| 1 | **pending 期间后续消息静默丢弃** | 🔴 严重 | 持续过载，EAGAIN 频繁 | 高（10000 TPS 过载时） |
| 2 | **flush 出错 pending 静默丢弃** | 🔴 严重 | 对端断链/EPIPE/ECONNRESET | 低（但后果严重） |
| 3 | **返回语义变化，上层误判** | 🟠 中等 | 任何 EAGAIN 场景 | 始终存在 |
| 4 | **接收线程负载增加，延迟回报** | 🟡 中等 | pending 积压大时 | 中 |
| 5 | **断链时 pending 静默丢弃** | 🟡 中等 | 断链时有 pending | 低 |
| 6 | **堆分配抖动** | 🟢 轻微 | 每次 EAGAIN | 中 |
| 7 | **心跳可能丢失** | 🟢 轻微 | 过载时心跳恰遇 pending | 低 |

##### 7.4.2.9 建议的修复方向

1. **#1 最严重**：`pending_buf_` 改为**队列**（`std::deque<std::vector<char>>` 或环形缓冲），pending 满时新消息排队而非丢弃；或 pending 忙时让上层**返回负值重试**（修改上层判断为 `ret != len` 而非 `ret < 0`）。
2. **#2 和 #5**：flush 出错 / `close_ch` 时触发 `deal_send_error` 回调，让上层感知消息丢失。
3. **#3**：引擎层改为 `if (ret != data_len)` 判断发送是否完整，不完整时重试或报错。
4. **#4**：`flush_pending` 加**最大补发次数**限制（如一次最多补发 10 次），避免长时间阻塞接收。
5. **#6**：`pending_buf_` 预分配固定容量（如 4096 字节），`assign` 改为 `memcpy` 复用。

#### 7.4.3 正面影响

1. **消除忙等自旋**：引擎线程在发送受阻时立即返回，不再 `CPU_PAUSE()` 钉死，可继续处理后续消息。
2. **尾部延迟显著改善**：多客户 P90 ↓66%、P95 ↓34%；单客户 P90 ↓26%。
3. **0 失败稳定**：所有场景（原版/异步、单/多客户、5000/10000 TPS）均 0 失败，无数据丢失。
4. **改动局部化**：核心改动集中在 `aio_tcp` 层 + 少量 `wait_poll` 支持，不影响 `tcp_ch` 及上层协议逻辑。

#### 7.4.4 未解决的问题（根本瓶颈仍在）

- **P90/P95 尾部仍受 FTE 能力限制**：10000 TPS 下 P90 仍达 ~2000ns、P95 仍达 ~10000ns，因为**背压源头是 FTE 单线程 asio 处理能力不足**，非阻塞发送只消除了客户端侧的忙等，无法提升 FTE 吞吐。
- **P50 与 P90 的差距**：稳态 P50（~300ns）优秀，但过载时尾部仍明显，说明**背压传导并未完全消除**，只是从"忙等阻塞"变为"排队积压"。

#### 7.4.5 原始方案（不优化）的负面影响对照分析

> 对照维度：若**不采用**非阻塞发送 + 写就绪通知优化，继续沿用原始 `tcp_ch::send_msg_fc`（§2.1：`send(fd, buf, len, 0)` 阻塞模式 + EAGAIN 时 `CPU_PAUSE()` 忙等自旋），会持续承受如下负面影响。这些正是 §7.4.2 优化后缺陷的**反面**——优化方案以"增加少量丢弃/复杂度风险"换取了"消除忙等 + 降低尾部延迟"。

##### 7.4.5.1 原始方案代码回顾

```cpp
// tcp_ch.cpp:40-59（原始实现）
int32 tcp_ch::send_msg_fc(char *pmsg, int32 len) {
  while (is_work()) {
    ret = send(sysfd, pmsg + wlen, len - wlen, 0);  // flags=0 阻塞模式，MSG_DONTWAIT 被注释
    if (ret == len - wlen) return len;               // 全部发送成功
    else if (ret >= 0) { wlen += ret; continue; }    // 部分发送，继续
    else {
      if (errno == EAGAIN || EWOULDBLOCK || EINTR) {
        CPU_PAUSE(); continue;   // ← 内核缓冲满时忙等自旋
      } else
        return LBERR_OBJ_WRITE_FAIL;
    }
  }
}
```

##### 7.4.5.2 🔴 严重：引擎线程忙等自旋，整条链路被钉死

`send()` 用阻塞模式（`flags=0`），发生 `EAGAIN` 时 `CPU_PAUSE()` **忙等自旋**：
- 引擎线程**不释放 CPU、不让出线程**，持续自旋直到内核缓冲腾出空间
- 引擎线程是**单线程串行**处理发送 + 接收 + 心跳（§5.6.1），忙等期间**无法处理任何其他事件**
- 忙等时长取决于对端消费速度（毫秒~百微秒级），完全不可控

##### 7.4.5.3 🔴 严重：批量尾部延迟（背压放大，P90/P95 拖尾根因）

§5.6.2 背压传导链已证明：
```
一次 EAGAIN → 引擎线程忙等 → 期间 send_queue_ 积压 N 条
  → 忙等结束恢复 → 积压消息被批量处理
  → 每条积压消息的排队时间 ≈ 忙等时长 → 被计入延迟
结果：一次 EAGAIN → 一批消息延迟集体升高 → P90/P95 拖尾
```
- **实测证据**：原始方案 FTE P95=2850ns（GOne 的 9.4 倍）、最大 9294μs
- 忙等把"单个请求的阻塞"放大为"一批请求的排队延迟"，是尾部延迟的**结构性根源**

##### 7.4.5.4 🟠 严重：CPU 空转浪费，拖累同机进程

- `CPU_PAUSE()` 忙等是**非阻塞自旋**，占满一个物理核心
- 高 TPS 下 EAGAIN 频繁，核心大量时间在**空转**而非做有效工作
- 实测 FTE 与 GOne 同机运行时，FTE 忙等空转**抢占 CPU**，导致 GOne 平均延迟从 2159ns 劣化到 5757ns（§1.2 注）
- 在多进程共享 CPU 的部署下，忙等会**放大系统整体延迟抖动**

##### 7.4.5.5 🟠 中等：接收与心跳被阻塞

引擎线程忙等期间：
- **回报接收延迟**：`deal_recv` 无法执行，回报处理不及时，回调延迟增大
- **心跳超时风险**：心跳发送/保活被推迟，多次忙等叠加可能导致对端超时断链（对应历史 `-22=LBAPI_ERR_LINK_DISCONNECTED`）

##### 7.4.5.6 🟡 中等：吞吐上限受限（TPS 天花板）

- 忙等使引擎线程有效处理能力下降，实际 TPS 低于理论值
- §5.6.3 实证：FTE 实际 8503~9439 vs 请求 10000，**缺口 5~15% 正是忙等背压的量化证据**
- 非阻塞发送 + 异步补发可让引擎线程在发送受阻时继续处理下一条，**吞吐不再受忙等拖累**

##### 7.4.5.7 🟡 中等：延迟抖动大，不可预测

- 忙等时长取决于内核缓冲释放时机与对端消费节奏，**不可预测**
- 秒级/毫秒级抖动（最大 9294μs），远高于 GOne（最大 2987μs）
- 对**延迟敏感的金融交易场景**是致命缺陷——无法提供稳定的延迟上界

##### 7.4.5.8 🟡 中等：与 GOne 差距持续放大

| 指标 | 原始 FTE | GOne | 差距 |
|:---|---:|---:|:---|
| P50 | 418ns | 245ns | 1.7x |
| P90 | 599ns | 277ns | 2.2x |
| **P95** | **2850ns** | **304ns** | **9.4x** |
| 最大 | 3178μs | 2987μs | 接近 |

- GOne 硬件极速无忙等，P50→P95 平坦（245→304ns，跨度 59ns）
- FTE 忙等导致 P95 为 GOne 的 9.4 倍，**若不做优化，尾部差距无法收敛**

##### 7.4.5.9 🟢 轻微：可扩展性差

- 单线程忙等架构，无法通过增加线程扩展吞吐
- 每增加一条链接/客户，忙等竞争加剧，尾部延迟进一步恶化

##### 7.4.5.10 原始方案 vs 优化方案对比总结

| 维度 | 原始方案（忙等） | 优化方案（非阻塞+异步） |
|:---|:---|:---|
| 引擎线程行为 | EAGAIN 时忙等自旋，钉死 | 立即返回，交由 epoll 异步补发 |
| 尾部延迟（P95） | 2850ns（GOne 9.4x） | 多客户 7103ns（10000TPS 过载）/ 单客户 1022ns |
| 吞吐（TPS） | 受忙等拖累（缺口 5~15%） | 不受忙等拖累 |
| CPU 利用 | 空转浪费，拖累同机进程 | 有效利用，无空转 |
| 接收/心跳 | 忙等期间被阻塞 | 正常处理 |
| 可靠性风险 | **低**（忙等保证最终发出） | **中**（§7.4.2 静默丢单风险） |
| 延迟可预测性 | 差（秒级/毫秒级抖动） | 较好（稳态 P50 ~300ns） |

> **权衡结论**：原始方案以"忙等保证不丢消息"换取"高尾部延迟 + CPU 空转 + 吞吐受限"；优化方案以"增加少量静默丢单/复杂度风险（§7.4.2）"换取"消除忙等 + 稳定低延迟 + 高吞吐"。**对金融交易场景，延迟稳定性优先于极小概率的丢单风险**，优化方向正确，但需通过 §7.4.2.9 的修复建议消除丢单缺陷。

### 7.5 后续建议

| 优先级 | 建议 | 依据 | 预计收益 |
|:---:|:---|:---|:---|
| 🔴 治本 | **FTE 侧多线程 asio**（§6.2 方案六）：`fte/src/main.cpp:512` 的 `io_service_.run()` 改多线程（2~4 个 ios_thread），或按连接类型拆分 io_service | §5.6 已证明背压源头是 FTE 单线程处理能力 < 发单速率 | P90/P95 ↓80%+（背压消失后尾部仅剩内核抖动） |

| 🟢 优化顺序 | 先治本（FTE 多线程）→ 再限流验证 → 最后绑核 | 非阻塞发送已落地，现有尾部主要来自 FTE 过载 | — |

> **总结**：非阻塞发送 + 写就绪通知优化已成功落地（多客户 P90 ↓66%、P95 ↓34%，0 失败），消除了客户端侧忙等自旋；但 P90/P95 的根本瓶颈仍是 **FTE 单线程 asio 处理能力**，需协调 FTE 团队做多线程 asio（治本）或压测时限流（治标）。

## 九、GOne vs gw 网卡抓包性能对比（2026-09-18）

> 对 GOne（FPGA）counter 也采用与 §8 相同的**网卡抓包时间分析**方法（`api_net_time_capture`，详见 `mock/client/api_net_time_design.md`），测量委托从进入 API（`api_arrive_time_ns`）到真正从网卡发出的端到端延迟，与 gw（FTE）做全面对比。**同一测试环境、同一方法、同一测试目录（仅登录用例），对比公平。**

### 9.1 网卡抓包程序扩展（支持 GOne 协议）

GOne 委托包结构与 gw 不同，已扩展 `api_net_time_capture` 支持 `--proto gone`：

| 项 | gw (FTE) | GOne (FPGA) |
|:---|:---|:---|
| 包结构 | PktNewHeader 8B + TradeOrderReq 106B + 校验和 4B = 118B | g1_msg_head 16B + order_req 48B = 64B |
| msg_id | 1003（**大端**） | **1001**（**小端**） |
| client_seq_id 字段 | TradeOrderReq.client_seq_id（偏移 62） | order_req.cust_req_no（偏移 40） |
| client_seq_id 字节序 | 小端（build_order_msg memcpy host） | 小端（`body->cust_req_no = req.client_seq_id` 直接赋值） |
| 委托发送端口 | 33001（FTE 单一链路） | **44002（Core 链路）**，44001 为 GW 登录链路 |
| 校验和 | 有（4B） | 无 |

> **关键**：GOne 委托走 **Core 链路（44002）**，登录走 GW 链路（44001）。抓包须过滤 44002 端口。GW 登录应答 `trade_port` 填 `core_port_`（gone_counter_server.cpp:211）。

### 9.3 API 内处理耗时对比（mock_client perf 报告）

| 指标 | gw (FTE) | GOne (FPGA) | 差异 |
|:---|---:|---:|:---|
| 实际 TPS | 7797.97 | 9458.79 | GOne ↑21% |
| P50 | 290 ns | 421 ns | gw 优 ↓31% |
| P90 | 571 ns | 581 ns | 相当 |
| P95 | 2836 ns | **732 ns** | GOne 优 ↓74% |
| 失败 | 0 | 0 | — |

> **API 内处理**：gw 的 P50（290ns）优于 GOne（421ns）——gw 会话已迁成员（`local_session_`）省去查找；但 **gw 的 P95（2836ns）远高于 GOne（732ns）**——gw 尾部受 FTE 单线程 asio 背压影响（§5.6）。GOne 是 FPGA 硬件，处理能力稳定（P50→P95 跨度仅 421→732ns）。

### 9.5 内核协议栈 + 网卡排队差额（端到端 - API 内）

| 指标 | gw | GOne | 差异 |
|:---|---:|---:|:---|
| P50 | 2,566 ns | 2,776 ns | 相当 |
| P90 | 2,897 ns | 3,266 ns | gw 略优 |
| P95 | 3,790 ns | 3,967 ns | 相当 |

> **内核+网卡排队是公共基线**：两者差额均在 ~2.5-4μs 范围，与柜台无关，是内核协议栈 + ::send() + 网卡排队固有开销。最小延迟 ~2.3μs 为内核协议栈基线。

### 9.6 关键结论

1. **API 内处理**：gw P50（290ns）优于 GOne（421ns），但 **gw P95（2836ns）远高于 GOne（732ns）**——gw 尾部受 FTE 背压限制，GOne FPGA 硬件延迟稳定（P50→P95 跨度仅 311ns）。
2. **网卡端到端**：两者 P50/P90 接近（gw 2856/3468 vs GOne 3197/3847，gw 略优），但 **P95 gw(6626) 明显高于 GOne(4699)**——gw 尾部拖尾来自 FTE 背压传导。
3. **内核+网卡排队**：两者公共基线 ~2.5-4μs，与柜台无关。
4. **吞吐**：GOne 实际 TPS 9458 > gw 7798，GOne 处理能力更强（FPGA 硬件），gw 受 FTE 单线程 asio 限制。
5. **GOne 最大 4.2ms 异常**：GOne 虽有 FPGA，但最大延迟 4.2ms（远高于 P95 4.7μs），为偶发调度抖动或 mock 环境干扰，需关注但非系统性。

### 9.7 综合建议

| 维度 | 结论 |
|:---|:---|
| 延迟稳定性 | **GOne 更优**（P95 732ns vs gw 2836ns，FPGA 硬件无背压） |
| 平均/中位延迟 | gw 略优（P50 290 vs 421ns，会话迁成员优化生效） |
| 吞吐能力 | GOne 更优（9458 vs 7798 TPS，FPGA 处理能力） |
| gw 优化方向 | FTE 侧多线程 asio（§6.2 方案六）消除背压，P95 可向 GOne 靠拢 |
| 网卡排队 | 两者公共基线，无法通过柜台优化消除 |
