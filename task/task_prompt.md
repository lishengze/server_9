# task_prompt.md — Agent 对话模板（面向不同工作场景）

> 目的：总结一套**规范化的与 Agent 对话的模板**，面向不同工作场景，使 Agent 能更好地理解当前工作场景，从而更好地完成任务。
> 用法：用户发起任务时，可按对应场景模板组织输入；Agent 也可按模板结构主动澄清、收集信息。
> 总原则：**上下文清晰、目标明确、约束可见、交付物可验收**。

---

## 0. 通用对话框架（所有场景共用）

无论哪种场景，一段高质量的任务输入都应包含以下要素：

| 要素               | 说明                       | 示例                                        |
| ------------------ | -------------------------- | ------------------------------------------- |
| **场景类型** | 属于六类中的哪一类         | "这是一个研究代码的任务"                    |
| **目标**     | 要达成什么结果（可验收）   | "掌握 80300101 数据加载流程"                |
| **上下文**   | 相关文件/目录/环境         | "代码在 otcsrc/lbm/lbm_jstp_system_global/" |
| **约束**     | 边界、风格、平台、环境要求 | "在 docker otc 内编译部署"                  |
| **交付物**   | 期望的输出形式             | "输出一份 analysis.md 文档"                 |
| **验收标准** | 怎么算完成                 | "文档覆盖流程/技术点/场景/交互"             |

---

## 1. 场景一：学习文档知识

**适用**：掌握某文档、规范、接口、协议的内容与要点。

```
【场景】学习文档知识
【目标】掌握 <文档> 的核心内容，能回答相关问题
【文档位置】<路径，如 study/knowledge_base_system/03_全局节点开发.md>
【学习深度】<概览 / 理解 / 掌握细节>
【重点问题】(可选) <最关心的几个问题>
【交付物】<可选：学习笔记 / 问答 / 总结文档>
【验收标准】能不看文档说出核心要点；能定位到关键路径
```

**Agent 应输出**：文档结构梳理 → 核心概念/流程 → 关键路径/配置 → 常见坑 → 与现有知识的关联。

---

## 2. 场景二：研究代码，掌握代码知识

**适用**：深入分析某个模块/功能/工程的代码，掌握实现原理。

```
【场景】研究代码
【目标】掌握 <模块/功能> 的实现原理与运行流程
【代码位置】<路径，如 otcsrc/lbm/lbm_jstp_system_global/>
【研究维度】<功能清单 / 运行流程 / 技术特点 / 业务场景 / 外部交互>
【触发方式】<功能如何触发 / 与外部如何交互>
【交付物】<可选：分析文档 / 流程图 / 时序图 / 类图>
【验收标准】能说清每个功能的流程、技术特点、业务场景、外部交互
```

**Agent 应输出**：代码结构 → 关键类/函数 → 数据流转 → Mermaid 图（流程/时序/类图）→ 关键路径 → 潜在坑点。

---

## 3. 场景三：基于当前代码，提出开发需求并完成开发测试

**适用**：在现有代码基础上新增/修改功能，并完成开发与测试。

```
【场景】开发需求 + 开发测试
【目标】实现 <功能描述>
【需求背景】<为什么做 / 业务价值>
【现状代码】<涉及的文件/模块/现有模式>
【功能点】<新增/修改的功能点清单>
【约束】<平台 x86/arm、环境 docker、风格、兼容性、性能>
【测试要求】<是否需 mock_client 测试 / 测试案例>
【交付物】<代码 / 文档 / 测试结果>
【验收标准】编译通过、测试通过、符合现有架构与命名风格
```

**Agent 应输出**（遵循 8 步法/现有开发模式）：

1. 先检索知识库与现有实现 → 2. 规划任务清单 → 3. 编码（LBM/Atom/DAO 分层）→ 4. 编译部署（docker + CMake）→ 5. 开发/更新测试案例 → 6. 回归测试 → 7. 多轮复查 → 8. 沉淀（日志+知识+Prompt）。

---

## 4. 场景四：面向当前代码，提出测试需求并完成测试

**适用**：对现有功能设计测试案例并执行测试。

```
【场景】测试需求 + 测试执行
【目标】测试 <功能号/功能>，验证 <预期行为>
【被测代码】<功能号、模块、路径>
【测试范围】<功能点清单：正向/反向/边界/异常>
【测试数据】<是否需要构造数据，如 DBF/内存表/配置文件>
【测试环境】<docker otc、mock_client、KGMS 等>
【预期结果】<每个用例的预期：成功/失败、回报字段、数据校验>
【交付物】<测试案例文档 / 测试结果 / 问题记录>
【验收标准】用例覆盖功能点，正反向均验证，结果有日志证据
```

**Agent 应输出**：测试案例文档（格式参考 `study/*/测试案例.md`）→ 构造测试数据 → 编写/运行测试 → 记录结果 → 分析失败根因 → 回归验证 → 沉淀。

---

## 5. 场景五：回答对于当前代码的疑问

**适用**：对某段代码/某个功能提出疑问，需要解释说明。

```
【场景】代码答疑
【疑问】<具体问题，如 "为什么 80300101 入参 key 是 LoadDataGlobal？">
【涉及代码】<文件/函数/行号，或粘贴代码片段>
【相关背景】<可选：上下文/已知信息>
【期望】<解释原理 / 指出根因 / 给出建议>
【交付物】<口头/书面解答>
【验收标准】解答准确、有代码依据、能指出关键路径
```

**Agent 应输出**：定位相关代码 → 解释原理/流程 → 给出依据（代码/日志/知识库）→ 若涉及修改给出建议。

---

## 6. 场景六：根据语言描述或文件，分析问题并给出解决方案

**适用**：根据报错、日志、配置文件或问题描述，定位根因并给出解决方案。

```
【场景】问题分析
【问题现象】<报错原文 / 日志片段 / 现象描述>
【相关文件】<配置文件 / 日志 / 代码路径>
【环境】<平台、docker、节点、版本>
【已尝试】(可选) <已做的排查>
【期望】<定位根因 / 给出解决方案 / 给出排查步骤>
【交付物】<分析结论 / 解决方案 / 修复代码>
【验收标准】根因明确（有证据）、方案可行、修复后验证
```

**Agent 应输出**（错误驱动学习流程）：

1. 记录报错原文（现象）→ 2. 检索知识库/历史排障是否有现成根因 → 3. 看日志/复现定位根因（不猜测）→ 4. 给出解法并验证 → 5. 把"现象→根因→解法"沉淀为知识。

## 7. 复盘触发 Prompt 模板（每日/每周/每月）

> 配合 `task/review/review_prepare.sh` 使用。**用户只需说"进行daily复盘 / weekly复盘 / monthly复盘"一句话即可触发完整流程**（见下方"一句话触发"说明）。

### 7.1 一句话触发（用户侧）

用户只需对 agent 说：
> **"进行daily复盘"**（或 weekly / monthly）

agent 收到后，自动执行 §7.2 的完整流程。

### 7.2 完整流程（Agent 侧执行）

```text
【复盘触发】进行 <daily/weekly/monthly> 复盘

第零步（关键，保证数据最新）：
  主动运行: bash task/review/review_prepare.sh <daily|weekly|monthly>
  生成/刷新最新复盘输入文件 task/review/<周期>_<日期>_input.md
  （不要依赖 cron 预生成的文件——若当天 cron 运行后又更新了 work_log，预生成文件会过时）

第一步：读取输入文件，执行复盘核心五问：
1. 各任务是否达标？有哪些瑕疵？
2. 哪些步骤高效、可固化复用？
3. 出现了哪些报错/卡点/低效问题？根因是什么？
4. 下次同类任务如何优化流程、规避问题？
5. 需要新增/优化哪些 Skill、知识库条目？

第二步：执行复盘成果五转化：
- 高效经验 → 标准化 Skill/流程模板
- 报错踩坑 → 问题解决方案知识库
- 流程瑕疵 → 优化通用工作 SOP
- 能力短板 → 靶向学习清单
- 优质案例 → 标杆案例库

第三步：更新知识库 + Prompt.md，写复盘报告到 task/review/<周期>_<日期>_report.md
```

> **为什么第零步关键**：`review_prepare.sh` 每次运行都会基于最新 work_log 重新生成输入文件，确保复盘不漏最后几小时的工作。cron 预生成的文件只是"兜底"，agent 触发时应主动刷新。

---

## 8. 模板使用建议

1. **用户侧**：发起任务时尽量按模板补全"目标/上下文/约束/交付物/验收标准"，信息越全，Agent 越准。
2. **Agent 侧**：任务信息不足时，按模板主动澄清缺失要素（尤其"目标"与"验收标准"）。
3. **收尾**：每个场景任务完成后，都执行 `task_rule.md` 的"自检清单"（日志/知识/Prompt/复查/提交/docker）。
4. **可组合**：一个任务可能横跨多场景（如"研究代码+开发+测试"= 场景二+三+四），按需组合对应模板。
